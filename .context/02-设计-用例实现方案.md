### 4.1.1 “用户注册与登录”用例实现的设计方案

“用户注册与登录”功能的实现由业务逻辑层”AuthController”对象在服务端完成：它读取数据层”User”对象提供的盐值与密码摘要并比对，判断账号与密码是否合法，随后签发访问令牌与刷新令牌并建立会话。密码摘要与签名密钥均不出服务端，前端只保存令牌。具体实现过程见图4-1所描述的用例设计顺序图。

**[图4-1 知音漫卷系统”用户注册与登录”用例设计顺序图]**

首先，用户通过界面层”LoginView”对象输入账号与密码并提交，该对象向业务逻辑层”AuthController”对象发消息 login(account, password)。“AuthController”对象在服务端经数据操作接口读取数据层”User”对象的记录（含盐值与密码摘要），随后调用该对象的 verifyPassword(password, salt, passwordHash)，完成加盐哈希比对并返回校验结果。

校验通过后，“AuthController”对象通过自身内部方法 issueJWT(userId) 以服务端密钥签发具有有效期的访问令牌，并通过 issueRefreshToken(userId, deviceId) 生成刷新令牌，再将用户信息与两枚令牌返回”LoginView”对象；“LoginView”对象调用 setSession(userInfo, token) 缓存会话，并跳转至阅读器主界面。访问令牌过期后，前端以刷新令牌调用 refreshToken(refreshToken) 换取新的令牌对，刷新令牌每次刷新即轮换。若账号不存在或密码不匹配，“AuthController”对象返回对应的认证错误，“LoginView”对象提示失败原因并保留用户已输入的内容，交互回到输入步骤。同一账号的失败登录次数达到阈值后触发短时锁定。

### 4.1.2 “导入并解析文档”用例实现的设计方案

“导入并解析文档”功能通过业务逻辑层”DocumentParser”对象按格式分派解析器、提取图片引用并上传资源，最终生成数据层”Document”对象并加入书架。具体实现过程见图4-2所描述的用例设计顺序图。

**[图4-2 知音漫卷系统”导入并解析文档”用例设计顺序图]**

读者在书架界面选择本地文件后，“LibraryView”对象向”DocumentParser”对象发消息 parse(file)。“DocumentParser”对象调用内部方法 dispatchParser(format)，依据文件格式选择 EPUB、TXT 或 Markdown 解析器，随后调用 matchImageRefs(text) 以正则匹配方式识别文本中的图片引用标记（Markdown 图片语法、[image:xxx] 标记与 HTML img 标签等），并记录其在段落中的上下文位置。

解析完成后，“DocumentParser”对象创建数据层”Document”对象，写入元数据、段落顺序与图片引用信息，并向外部系统”对象存储／CDN”发消息 uploadResource(file, images) 上传原始文件（该上传由服务端内部转存至对象存储／CDN，前端不直接接触对象存储）；上传成功后调用 setResourceUrl(resourceUrl) 回写资源地址。图片资源不在导入阶段上传，改由「图文混排阅读」用例在图片首次进入视口时按需上传。最后将文档对象返回”LibraryView”对象，由后者调用 addToShelf(document) 加入书架并提示”解析完成”。

若文件格式不受支持或解析失败，“DocumentParser”对象捕获异常并返回失败原因，文档不加入书架；若资源上传失败，则保留本地解析结果并将文档标记为”仅本地可见”，待网络恢复后重试上传。同一文档重复导入时以内容哈希去重：EPUB 按 spine 顺序拼接各章节正文与资源内容后计算 SHA-256，TXT 与 Markdown 按归一化后的正文文本计算 SHA-256，以免仅因容器元数据（如打包时间）不同而误判为新文档；同一用户的 (owner_id, content_hash) 联合唯一，解析过程不修改用户的原始文件。

### 4.1.3 「图文混排阅读」用例实现的设计方案

「图文混排阅读」功能通过业务逻辑层「RenderController」完成 DOM 构建、图片按需加载与内存回收，并以数据层「ImageResource」保存图片的本地缓存。具体实现过程见图4-3所描述的用例设计顺序图。

**[图4-3 知音漫卷系统「图文混排阅读」用例设计顺序图]**

读者打开文档后，「ReaderView」对象调用 renderDocument(doc) : void，并向「RenderController」对象发消息 render(doc) : void。「RenderController」对象构建段落与图片占位容器：按虚拟滚动策略，正文仅保留视口上下若干屏范围内的段落节点，其余以估算高度占位；随后调用 observeImages(container) : void 注册视口监听。

在滚动过程中，当某个图片占位容器进入视口时，「ReaderView」对象向「RenderController」对象发消息 loadImage(url) : Blob。「RenderController」对象先调用数据层「ImageResource」对象的 isCached() : bool 查询本地缓存，由后者通过本地存储接口 getImageBlob(cacheKey) : Blob 读取 IndexedDB：命中则直接返回 Blob 并渲染；未命中则向「ServerAPI」发消息 fetchImage(url) : Blob 取得图片，调用 putCache(cacheKey, imageBlob) : void 写入缓存后再渲染。若请求失败或超时，则调用 renderRetryPlaceholder(url) : void 渲染重试占位，不阻塞正文阅读。每轮加载结束后调用 recycleInvisible() : void 回收不可见图层：图片离开视口时清空其对象地址并释放 Blob，但保留 IndexedDB 中的副本，以便再次进入视口时取回。

该循环在滚动过程中反复执行直至文档阅读完毕。图片未进入视口时不发起网络请求；图片与正文段落保持顺序一致；缓存容量达到上限时按最近最少使用（LRU）策略淘汰：图片缓存上限为 200MB 或单文档 300 张（先到者为准），音频缓存上限为单文档 60MB，超出时淘汰最后访问时间最早的条目；淘汰只影响内存与对象地址，IndexedDB 中的副本仍保留。

### 4.1.4 “逐句高亮跟读”用例实现的设计方案

“逐句高亮跟读”是本系统最具特色的用例，其实现由业务逻辑层”ReadAlongController”对象负责句子切分、TTS 调度、音频映射与游标推进，数据层”Sentence”与”AudioClip”对象分别保存句子边界与”句子→音频片段”的映射。具体实现过程见图4-4所描述的用例设计顺序图。

**[图4-4 知音漫卷系统”逐句高亮跟读”用例设计顺序图]**

用户在播放控制条上选择音色与语速后点击”逐句跟读”，“PlaybackBar”对象向”ReadAlongController”对象发消息 startReadAlong(sentenceList, voice, rate)。“ReadAlongController”对象调用 splitSentences(text)，基于中文标点（。！？；等）与边界规则将正文切分为句子列表，并通过数据层”Sentence”对象的 createSentences(offsets) 持久化句子边界与段内偏移。

随后进入逐句循环：对于第 i 句，“ReadAlongController”对象先向外部系统”TTS 语音合成服务”发消息 synthesize(text[i], voice, rate) 取得音频片段，将其写入数据层”AudioClip”对象并缓存；接着向业务逻辑层”AudioPlayer”对象发消息 play(clip[i])，由该对象复用同一个音频元素播放并管理预加载队列。播放期间”ReadAlongController”对象向”ReaderView”对象发消息 highlightSentence(i) 高亮第 i 句，并调用 scrollToAnchor(sentence[i].anchor) 将容器自动滚动至高亮位置。音频播放结束时触发 onended 事件，“AudioPlayer”对象回调”ReadAlongController”对象的 advanceCursor(i) 方法，将游标推进至 i+1 并回到合成步骤。

为减少句间停顿，控制器始终预先合成后续句子，缓冲不少于 2 句。若 TTS 服务不可用或合成失败，则降级为浏览器原生 SpeechSynthesis 接口；仍不可用时提示”当前环境不支持语音朗读”并暂停跟读。若读者在高亮推进过程中手动回翻或跳读，则暂停自动滚动并保留当前高亮位置，读者点击”继续跟读”后由 holdCursor(i)／resumeFrom(i) 平滑接管。单句合成失败不中断整体流程，跳过该句继续；切换前后台或息屏时保存当前句子索引以便恢复。

*表4-1 句子切分边界规则*

| 规则 | 说明 |
| R1 句末标点切分 | 。！？… 及其组合（？！、！？、……）视为句末边界；标点归属前一句，不单独成句 |
| R2 分号与冒号不切分 | ；、： 仅作句内停顿，不产生新句 |
| R3 引号与括号内的句末标点同样切分 | 配对收尾符号（”、））归属前一句，下一句不得以收尾符号开头 |
| R4 连续省略号只算一次边界 | …… 与 ．．．．．． 均按一个句末边界处理，不产生空句 |
| R5 缩写与小数不切分 | 句点两侧均为数字（如 3.14），或命中缩写白名单（如 Mr.、No.）时，句点不作边界 |
| R6 段落内换行按句内空白处理 | 换行、制表符与连续空格在切分前归一为单个空格 |
| R7 切分前先归一化 | 剔除段落首尾空白与零宽字符；句子的起止偏移以归一化后的段落文本为准 |
| R8 超长句兜底 | 单句超过 200 字时在最近的 、、， 处强制切分；仍无标点则按 200 字硬切，保证单句音频时长可控 |
| R9 空句不得入表 | 纯标点、纯空白或长度为零的片段一律丢弃 |
| R10 索引稳定性 | 文档解析结果不变时句子索引保持稳定；切分规则变更视为内容升级，须重新生成句子表与音频缓存 |

说明：规则以段落为第一层边界，句子不跨段落；切分结果写入 T_Sentence，与 sentence_index 一一对应，索引自 0 起连续编号。

### 4.1.5 “跨设备进度同步”用例实现的设计方案

“跨设备进度同步”功能通过业务逻辑层”SyncController”对象完成云端进度拉取、本地记录比对与合并裁决，数据层”ReadingProgress”对象保存文档标识、设备标识、位置锚点、时间戳与版本号。具体实现过程见图4-5所描述的用例设计顺序图。

**[图4-5 知音漫卷系统”跨设备进度同步”用例设计顺序图]**

读者在新设备打开同一文档时，“ReaderView”对象向”SyncController”对象发消息 syncProgress(docId, deviceId)。“SyncController”对象先向外部系统”云端存储服务”发消息 listProgressByDocument(userId, docId)，取得该用户在该文档上的全部设备进度记录与版本号；再调用数据层”ReadingProgress”对象的 loadLocal(docId) 读取本机进度记录。

随后”SyncController”对象调用 merge(local, remote) 合并双方记录：跨记录按唯一标识并集合并；阅读进度取较新者并施加不回退保护（较新记录的位置早于本机已读位置时保留较前的位置），被舍弃的一份以 superseded 写入冲突记录供读者查看，不静默丢弃。并区分三种情形：云端无记录时以本地进度为准，调用 commitChanges(localProgress, 0) 首次上报；版本一致表示无新变更，跳过合并直接进入锚点定位；版本号不一致且无法自动合并时，转入”同步冲突处理”用例。

合并完成后，“SyncController”对象调用 updateAnchor(chapter, paragraph, offset) 更新进度对象，并向”ReaderView”对象发消息 locateTo(anchor)，由后者调用 scrollToAnchor(anchor) 将页面滚动至上次阅读位置，实现无缝续读。若锚点定位失败（文档已变更或段落缺失），则降级为按章节起始位置定位并提示读者。每台设备具有唯一设备标识，同一设备的重复同步请求被识别并忽略；同步采用增量方式，仅上传与拉取发生变更的数据。

### 4.1.6 “同步冲突处理”用例实现的设计方案

“同步冲突处理”功能通过业务逻辑层”SyncController”对象提交变更、读取冲突集、判定可合并性并回写结果，数据层”SyncRecord”对象保存本地与云端版本号及冲突状态，界面层”ConflictDialog”对象承担冲突列表与差异内容的展示。具体实现过程见图4-6所描述的用例设计顺序图。

**[图4-6 知音漫卷系统”同步冲突处理”用例设计顺序图]**

“SyncController”对象向外部系统”云端存储服务”发消息 commitChanges(delta, baseVersion) 提交本地增量变更。云端存储服务检测到提交所携带的基准版本号与当前版本不一致，返回冲突响应及双方变更记录集。“SyncController”对象调用数据层”SyncRecord”对象的 saveConflict(localDelta, remoteChanges) 保存冲突快照，随后调用 tryAutoMerge(localDelta, remoteChanges) 逐段比对，判定是否可自动合并。

判定规则为：两端修改的记录标识不同（跨记录）时视为互不影响，直接并集合并；同一记录仅一方修改时取修改方；同一记录双方均修改、但修改的字段集合不相交（一方改名、另一方移动位置）时按字段级合并；字段集合相交时视为无法自动合并。判定为互不影响或可按字段合并的，直接合并并将结果提交云端并生成新版本号，不打扰读者；若无法自动合并，“SyncController”对象向”ConflictDialog”对象发消息 showConflicts(conflictList)，界面逐条展示冲突类型与双方差异，读者选择或合并要保留的变更项后，界面通过 chooseResolution(conflictId, side) 与 applyAndMerge() 将结果回传，由”SyncController”对象提交云端并调用 updateState(“已同步”) 更新同步状态。

若读者选择”稍后处理”，则保留冲突状态，界面持续显示冲突标识，未处理的冲突不阻止继续阅读；若提交因网络中断失败，则将合并结果写入本地待同步队列，联网后自动重试，未决冲突记录不丢失。冲突过程不阻塞读者的正常阅读。
