# 第2章 逐项选型说明

## 2.1 前端框架

选定 React 18 + Vite + TypeScript。理由如下。

（1）框架选择在本项目中属于低风险决策。五个功能模块中，仅「图文混排渲染与懒加载」与「逐句高亮跟读」两个模块直接依赖视图框架；文档解析、用户认证与数据管理、跨设备进度同步三个模块均为与框架无关的纯 TypeScript 模块。因此框架不应渗透到核心逻辑之中。

（2）长文档正文的节点数可达数万，若逐句高亮的推进触发框架级的差异渲染，将产生明显卡顿。据此确立设计约束：正文渲染层以引用（ref）与直接 DOM 操作实现，不参与框架的响应式或虚拟 DOM 更新；句子切分、语音调度、同步引擎等核心逻辑一律实现为无框架依赖的纯 TypeScript 模块，可独立进行单元测试。

（3）备选方案为 Vue 3 + Vite + TypeScript。若小组成员对 Vue 更为熟悉，可等价替换，本项目的其余选型不受影响。

## 2.2 文档解析与渲染

选定混合方案：以 epub.js 承担 EPUB 格式的解析工作（获取 spine 顺序与每一章的 Document），渲染层完全自研；退路为完全自研方案，即使用 JSZip 解压并由 DOMParser 解析 container.xml、OPF 与 spine。理由如下。

（1）需求已约定"将不同格式的文档统一转换为结构化数据，并对外提供标准化的内容接口"。若采用 epub.js 自带的渲染层，将绕过该接口，使 EPUB 与其他格式分属两套渲染管线。

（2）epub.js 的渲染默认在 iframe 内进行，正文元素不位于主文档，导致图片懒加载所用的 IntersectionObserver、自动滚动与句子高亮均需跨文档操作；且 epub.js 以 CFI 定位，与本项目内部的句子索引属于两套坐标系，须维护双向映射，调试成本不可控。

（3）《软件需求规格说明书》的分析类图已预设 DocumentParser（按格式分派解析器、提取图片引用）与 RenderController（DOM 构建、图片按需加载与内存回收）两个控制类。自研渲染与该设计一致；若采用 epub.js 的渲染层，上述两个类的职责将落空。

（4）自研渲染之下，PDF、TXT、Markdown 与 EPUB 共用同一渲染管线与同一套交互实现，功能模块之间的接口保持统一。

解析结果采用如下中间格式，与需求分析类图中的实体类对应：

Document{id, title, meta} → Chapter{index, title} → Paragraph{index, type, text} → Sentence{index, start, end, text}；图片引用记为 ImageRef{paraIndex, offset, src, alt}。

EPUB 内部的图片为压缩包内的相对路径，在解析阶段解为 Blob 并写入 IndexedDB，与「图文混排渲染与懒加载」模块的缓存机制直接衔接。

退路触发条件：若第 2 周验证发现 epub.js 的解析接口难以单独使用，则改用完全自研方案，预计增加工期约三人日。

## 2.3 后端与数据存储

选定自建服务端：Node.js + TypeScript（Fastify 框架）配合 SQLite 单文件数据库，JWT 令牌由本项目自行签发，数据访问采用参数化 SQL 或轻量数据访问层。

该选择直接对应 1.2 节的三条硬约束：C1 要求交付服务端与数据库部署脚本，编排文件与数据库初始化脚本即为该交付物；C2 要求令牌的生成与刷新自行实现；C3 要求以版本号实现条件更新。此外，AI 伴读与云端语音合成所需的密钥必须经服务端代理，服务端不可缺省（C7）。

不采用 Supabase、Firebase 等后端即服务方案，理由如下。

（1）此类方案不产生由本项目自建的服务端，无法满足 C1 的交付要求。

（2）Firebase 的离线缓存与多端同步由框架内部完成，将覆盖「跨设备进度同步与冲突协调」这一功能的核心实现，使该模块失去可交付的代码与设计内容。

（3）Firebase 不提供基于 REST 的标准条件请求；Supabase 的 REST 接口亦不提供 HTTP 条件请求语义，须自行以版本号列实现乐观并发。其相对自建服务端节省的工作量，不足以弥补 C1 的缺失。

（4）境外服务在国内网络环境下的可达性不满足 C5。

数据库选型说明：SQLite 以单文件形式随项目交付，无需独立进程，适配单机部署形态；若后续并发写入需求上升，可平滑迁移至 PostgreSQL，仅需在同一编排文件中增加一个服务。本项目不引入对象存储与内容分发网络，单机部署形态下并无必要，图片与音频缓存由前端的 IndexedDB 与服务端的本地文件系统承担。

接口约定：服务端提供阅读进度上报、阅读进度拉取、书签增量同步（含新增、删除、重命名）三组接口。所有写接口一律要求客户端携带版本号以执行条件更新，并以受影响行数区分"更新成功"与"检测到冲突"两种结果。

## 2.4 语音合成

选定本地自托管的 Kokoro-FastAPI 作为默认语音合成引擎，通过其提供的 OpenAI 兼容接口接入。理由如下。

（1）满足 C4 与 C5：默认路径不依赖任何付费接口，且可在无外网条件下完整运行。

（2）模型规模为 82M 参数，可在普通笔记本的中央处理器上运行，不需要图形处理器。

（3）采用 OpenAI 兼容的接口形状，与其他服务商共用同一套客户端实现，需求中"支持对接多种语音合成服务商"因而可在演示中以切换服务地址的方式直接验证。

（4）具备流式合成与压缩音频输出能力，配合前端的预加载队列可满足句间推进的延迟要求。

运行时采用分层与降级策略：

L1 默认层：本地自托管 Kokoro-FastAPI，经服务端代理调用，不直接暴露给前端。

L2 可选层：具备免费额度的国内云语音合成服务（具体额度与接口形状以各家官方文档为准），或 OpenAI 语音合成接口（持有密钥时用于音质对比）。该层仅作为可选实现，不作为默认路径，因此不构成对 C4 的违反。

降级层：浏览器原生语音合成接口，用于无网络或无可用引擎时，仅保证句子级高亮。该降级路径已在《软件需求规格说明书》2.2.4 节扩展交互动作 4b 中约定。

接口抽象：定义统一的语音合成引擎接口，提供三个实现——OpenAI 兼容实现，覆盖 Kokoro-FastAPI 及一切 OpenAI 兼容服务；云服务商原生实现，覆盖国内云服务商的自有 REST 接口与签名鉴权；浏览器实现，承担降级。服务商之间的接口形状差异由适配器吸收，前端与业务层不感知具体供应商。

已知风险与验证计划：Kokoro 的中文音色质量中等，其优势主要体现在英文。计划于第 3 周进行中文音色的对比实测，即同一段中文文本分别由 Kokoro 与国产开源方案合成，记录主观评分与合成延迟，实测数据用于最终确认默认层选型并纳入测试报告。若实测结果不可接受，则考虑以国产开源方案替换默认层；需注意后者模型规模明显较大，通常需要图形处理器，与本项目"普通笔记本"的部署约束存在冲突，因此须在第 2 周先行确认可用硬件条件。

## 2.5 AI 伴读（扩展功能）

选定 DeepSeek 作为伴读功能所使用的大模型，经服务端代理调用。理由如下：该服务提供 OpenAI 兼容的对话接口，可与语音合成共用同一套客户端与配置方式；国内网络可直连，满足 C5；调用成本较低。伴读场景选用通用对话模型而非推理模型，以控制响应延迟。密钥仅保存在服务端的环境变量中，满足 C7。

范围限制：本期仅实现"基于当前阅读段落上下文的问答"，不实现全文检索与向量检索。DeepSeek 不提供向量化接口（以官方文档为准），如需检索能力须另行选型，不在本期范围之内。

# 第3章 部署方案

## 3.1 部署形态

采用单机部署：由一台普通 Windows 笔记本同时承担前端静态资源、服务端、数据库与语音合成服务四个角色。各组件以容器编排方式组织（Docker Desktop 配合 WSL2 后端），亦可采用 Windows 原生方式运行，即由 Node.js 直接运行服务端、由 Python 虚拟环境运行语音合成推理服务，以避免对容器环境的依赖。

跨设备演示：同一无线局域网内的平板与手机以"笔记本局域网地址 + 端口"的方式访问前端，即可完整演示「跨设备进度同步」用例，验收效果与云端部署一致。

范围边界：局域网之外的公网访问不在本期范围之内，作为设计约束记录。服务端仍按可公网部署的形式组织，同一套编排文件可直接部署至云主机，以保留后续扩展路径。

## 3.2 对可行性评估中服务器配置的修订

《软件系统的需求构思及描述》可行性评估一节中记载"服务端：最低配置 2 核 4GB 云服务器即可支撑原型系统"。本文档将该配置修订为"普通 Windows 笔记本"，修订理由如下。

（1）语音合成默认采用本地自托管方案。将其与业务服务端部署在同一台机器上，可避免音频流经由公网往返，降低合成与播放延迟，并消除演示现场对网络的依赖。

（2）不新增付费云服务依赖，符合 C4 的成本约束。

（3）需求中的跨设备同步可在局域网内以多台真实设备完整演示，验收效果与云端部署一致。

（4）服务端与数据库仍以部署脚本的形式交付，C1 的交付要求不受影响。如需公网可达，将同一套编排文件部署至云主机即可，迁移成本约为半人日。

本节修订已同步落到《软件需求规格说明书》3.1 节（服务端最低配置改为普通 Windows 笔记本）与《软件设计规格说明书》1.2 节、4.4 节（单机部署、Fastify、SQLite），三份文档口径一致。

# 第4章 跨端同步范围与冲突策略

## 4.1 同步对象

跨端同步仅包含以下两类数据。

（1）阅读进度锚点：单值数据，描述某文档当前的阅读位置，包括章节索引、段落索引、段内偏移、滚动偏移与修改时间。

（2）书签集合：以客户端生成的唯一标识为逻辑主键，字段包括书签标识、文档标识、位置锚点、书签名称、创建时间、修改时间、版本号与删除标记（软删除墓碑）。

本项目不提供修改电子书正文的功能，也不提供为正文段落添加高亮标注的功能。因此同步数据中不包含任何正文内容与标注内容，数据量恒定且很小，同步功能的实现成本极低。

## 4.2 不同步内容

朗读高亮位置不参与跨端同步，以本机定位为准。理由如下：朗读高亮是"逐句跟读"过程中的瞬态运行状态，其位置完全由本机的播放进度与句子切分结果决定；且各端的句子切分结果可能因文档解析缓存不同而存在差异。将其纳入同步既无实际使用价值，又会引入高成本的并发冲突——同一位置的播放进度在不同设备上高频变化，几乎无法合并。故明确排除。该取舍同时使本项目无需实现操作变换（OT）或无冲突复制数据类型（CRDT）等复杂合并算法。

## 4.3 冲突场景与处理策略

合并原则为"并集合并、不静默丢弃"，即任何一方的数据都不会因另一方的后到达写入而被无声覆盖。各场景的处理策略如表4-1所示。

*表4-1 同步冲突场景与处理策略*

| 冲突场景 | 处理策略 |
| 两端各自新增书签（逻辑标识不同） | 并集合并，两端书签均保留，不构成冲突 |
| 两端对同一书签重命名 | 两个名称均保留，作为两条记录进入冲突列表，由读者选择其一或全部保留 |
| 一端删除书签，另一端修改（重命名或移动位置）同一书签 | 保留修改后的书签，不执行删除，并在冲突列表中标注"该设备曾删除此书签" |
| 两端均删除同一书签 | 结果一致，幂等，不构成冲突 |
| 阅读进度锚点在不同端不一致 | 取修改时间较新者，并作单调性保护：若较新记录的位置早于本地已读位置，则不回退，保留较前的位置，避免多端切换时出现阅读进度倒退 |

## 4.4 冲突检测手段

冲突检测依赖服务端的条件更新：所有写接口均要求客户端携带记录的版本号，服务端以"版本号匹配方可更新"的方式执行，受影响行数为零即判定为冲突，进而触发表4-1所列的"同时保留"策略。需要指出的是，仅采用"最新时间戳优先"的覆盖式写入无法检测冲突——覆盖式写入只会静默丢失数据而不产生任何冲突信号。因此，基于版本号的条件更新是冲突处理的前提，而非可选的优化手段。

## 4.5 与需求文档的差异说明

《软件需求规格说明书》1.2 节功能描述表在「同步冲突处理」一行中记载"预留逐段合并与操作变换（OT）算法的扩展接口"。本文档将该表述收敛为：不实现操作变换或无冲突复制数据类型算法，也不预留其接口。理由为同步范围已收敛至书签集合与阅读进度锚点，4.3 节所列冲突场景均可由"同时保留"策略无损解决，无需引入上述算法。

同时，《软件需求规格说明书》1.2 节「跨设备进度同步」一行中提及的"高亮记录"不参与同步，以本文档 4.2 节为准。上述收敛不改变需求的验收内容，仅缩小实现范围，相应设计约束见第 6 章 C10。

# 第5章 非功能需求指标的修正

## 5.1 修正说明

需求文档中"30 分钟内存不增长"的表述不能作为可验收指标：浏览器的垃圾回收为非确定性行为，JavaScript 堆占用在任何活跃应用中均呈锯齿状波动，其绝对数值"不增长"在技术上不可能成立。若照此表述验收，必然无法通过。因此将该指标改为以趋势与上限为判定口径，使其可测量、可复现。

## 5.2 修正后的指标口径

*表5-1 非功能需求指标修正对照*

| 原表述 | 修正后的表述 | 说明 |
| 30 分钟内存不增长 | 连续跟读 30 分钟后：（1）DOM 节点总数不超过当前渲染窗口上限，即视口窗口量的 3 倍以内；（2）JavaScript 堆占用首尾采样值之差不超过 10%；（3）DOM 节点数与堆占用均不随阅读时长呈线性增长。 | 以趋势与上限作为判定口径，可在浏览器开发者工具中直接测量 |
| 音频起播不超过 120ms | 在预加载缓冲命中的条件下，句间推进与音频起播延迟不超过 120ms；首次合成不计入本口径。 | 首次合成需等待推理服务响应，不可与缓冲命中情形纳入同一口径 |

## 5.3 达标所依赖的实现手段

上述指标并非自然达成，须以下列实现手段为前提。

（1）虚拟滚动。正文仅保留视口上下若干屏范围内的段落节点，其余以估算高度占位；节点渲染完成后回写实测高度并补偿滚动偏移，避免滚动条与阅读视角跳变；跟读高亮所在的句子强制保留在渲染范围之内，不因滚出视口而被销毁；自动滚动不以目标节点定位（目标节点可能尚未渲染），而按虚拟坐标换算滚动位置。

（2）图片内存回收。以对象地址方式生成的图片地址在使用完毕后必须显式释放，否则其对应的 Blob 不会被回收；图片离开视口时清空其地址属性并从内存缓存中移除，但仍保留在 IndexedDB 中，以便再次进入视口时取回。

（3）音频内存回收。音频不得使用 Web Audio 的解码接口转换为常驻内存的采样数据——未经压缩的采样数据体积远大于压缩音频，以 44.1kHz 单声道为例，每分钟约 5MB，长文档朗读将迅速耗尽内存。实现上采用音频元素播放压缩音频数据，仅保留"当前句与预加载若干句"的地址，其余释放并落回 IndexedDB。

（4）播放元素复用与资源注销。全程复用同一个音频元素，避免重复创建导致解码器初始化开销与资源泄漏；事件回调与观察器在生命周期结束时统一注销。

（5）检测方法。以浏览器开发者工具的内存面板进行堆快照对比，或以性能面板观察 JavaScript 堆占用与 DOM 节点数随时间的变化曲线，作为第 5.2 节指标的实测依据。
