# 知音漫卷 系统接口说明文档

第一组 · 软件工程课程设计 · 2026 年 10 月

本文档定义前端 Web 应用（ZhiYinClient）与自建服务端（ZhiYinServer）之间的接口契约。服务端同时承担**云端存储服务**、**图片资源代理**、**TTS 语音合成代理**与**AI 伴读代理**四种角色；前端不直接调用任何第三方服务，因此前端代码中不含任何服务密钥。

---

## 1. 通用约定

| 项 | 约定 |
|---|---|
| 基础路径 | `/api`，全部为 HTTPS + JSON（除标注为二进制的接口） |
| 字符编码 | UTF-8；时间一律为 ISO 8601 UTC 字符串（如 `2026-10-04T12:00:03.000Z`） |
| 认证 | `Authorization: Bearer <accessToken>`；除注册/登录/刷新外所有接口均需携带 |
| 访问令牌 | JWT（HS256，服务端环境变量密钥签发），有效期 **30 分钟**，载荷含 `sub`(userId)、`jti`、`iat`、`exp`、`typ:"access"` |
| 刷新令牌 | 服务端生成的 256 位随机串，**以哈希形式**存于 `T_Token`，有效期 **14 天**，每次刷新即轮换 |
| 设备标识 | 客户端首次启动生成 UUID 并持久化于 localStorage，登录与同步时作为 `deviceId` 上送，用于标识来源设备、避免同设备重复同步 |
| 条件更新 | 写接口一律在请求体中携带 `baseVersion`；服务端以"版本号匹配才更新"执行，受影响行数为 0 时返回 `409 SYNC_VERSION_CONFLICT` 及冲突信封 |
| 幂等 | 批量同步与二进制上传接口支持 `Idempotency-Key` 请求头（客户端生成 UUID）；服务端在 24 小时内对相同键返回首次结果，用于抵御重复提交 |
| 分页 | 查询接口统一使用 `page`（从 1 起）与 `pageSize`（默认 20，上限 100），响应含 `total`、`page`、`pageSize` |
| 请求追踪 | 响应头 `X-Request-Id`；错误响应体中回显同值，便于定位 |

**统一错误信封**（所有非 2xx 响应）：

```json
{
  "code": "AUTH_INVALID_CREDENTIAL",
  "message": "账号或密码错误",
  "details": {},
  "requestId": "req_8f3c1a"
}
```

`details` 承载该错误码特有的补充信息（如锁定截止时间、重复导入命中的 docId）。

## 2. 错误码总表

| HTTP | code | 含义 | details 内容 |
|---|---|---|---|
| 400 | `VALIDATION_FAILED` | 参数缺失或格式非法 | `{fields:["account"]}` |
| 401 | `AUTH_REQUIRED` | 未携带令牌 | — |
| 401 | `AUTH_TOKEN_EXPIRED` | 访问令牌过期，应调用刷新接口 | — |
| 401 | `AUTH_INVALID_CREDENTIAL` | 账号或密码错误（**不区分账号是否存在**，防用户枚举） | — |
| 401 | `AUTH_REFRESH_INVALID` | 刷新令牌无效、过期或已被轮换 | — |
| 401 | `AUTH_OLD_PASSWORD_WRONG` | 修改密码时原密码不正确 | — |
| 403 | `FORBIDDEN_NOT_OWNER` | 目标资源不属于当前用户 | — |
| 404 | `NOT_FOUND` | 资源不存在 | — |
| 409 | `CONFLICT_ACCOUNT_EXISTS` | 账号已被注册 | — |
| 409 | `CONFLICT_DOCUMENT_DUPLICATE` | 同一用户重复导入同一文档 | `{docId}`（已存在的文档） |
| 409 | `SYNC_VERSION_CONFLICT` | 版本号不匹配，详见冲突信封 | `{conflict:{...}}` |
| 413 | `PAYLOAD_TOO_LARGE` | 上传体量超过上限（见 §4.8，当前 500MB）；`POST /api/documents` 的段落数超过 `MAX_PARAGRAPHS` 也走这条 | — |
| 415 | `UNSUPPORTED_FORMAT` | 文件格式不在 EPUB/TXT/Markdown 之列 | `{fileFormat}` |
| 422 | `PARSE_FAILED` | 服务端校验解析结果失败（段落/句子结构非法） | `{reason}` |
| 423 | `ACCOUNT_LOCKED` | 连续失败登录次数达阈值，账号短时锁定 | `{lockedUntil}` |
| 429 | `RATE_LIMITED` | 请求过于频繁 | `{retryAfter}`（秒） |
| 500 | `INTERNAL_ERROR` | 服务端内部错误 | — |
| 502 | `UPSTREAM_TTS_FAILED` | 语音合成上游失败（含本地推理服务不可用） | `{engine}` |
| 502 | `UPSTREAM_AI_FAILED` | AI 伴读上游失败 | `{provider}` |
| 504 | `UPSTREAM_TIMEOUT` | 上游超时 | `{engine}` |

账号锁定策略：连续失败 **5 次** 锁定 **15 分钟**，期间登录返回 `423`；锁定截止时间随 `details.lockedUntil` 返回，前端据此提示剩余时间。锁定计数与截止时间存于 `T_User.fail_count` / `T_User.locked_until`。

## 3. 认证接口

### 3.1 注册

`POST /api/auth/register`

```json
{ "account": "13800000000", "password": "********", "nickname": "读者甲" }
```

`201`：

```json
{ "userId": "u_2f1c", "account": "13800000000", "nickname": "读者甲", "createdAt": "2026-10-04T12:00:00.000Z" }
```

错误：`400 VALIDATION_FAILED`、`409 CONFLICT_ACCOUNT_EXISTS`（密码长度 ≥ 8，账号唯一）。

### 3.2 登录

`POST /api/auth/login`

```json
{ "account": "13800000000", "password": "********", "deviceId": "dev_7a91..." }
```

`200`：

```json
{
  "accessToken": "eyJhbGciOi...",
  "refreshToken": "rt_9f0c...",
  "expiresIn": 1800,
  "user": { "userId": "u_2f1c", "account": "13800000000", "nickname": "读者甲" }
}
```

错误：`401 AUTH_INVALID_CREDENTIAL`、`423 ACCOUNT_LOCKED`、`429 RATE_LIMITED`。
流程：服务端读取 `T_User` 记录 → 用 `salt` 与 `password_hash` 完成加盐哈希比对 → 校验通过则签发访问令牌与刷新令牌，并写入 `last_login`、清零 `fail_count`。**密码哈希不下发到客户端**。

### 3.3 刷新令牌

`POST /api/auth/refresh`

```json
{ "refreshToken": "rt_9f0c...", "deviceId": "dev_7a91..." }
```

`200`：同 3.2 的 `accessToken` / `refreshToken` / `expiresIn`（刷新令牌轮换，旧的立即失效）。

### 3.4 退出登录

`POST /api/auth/logout` → `204`，请求体 `{ "refreshToken": "rt_9f0c..." }`，服务端删除该令牌记录。

### 3.5 查询与修改账号信息

`GET /api/users/me` → `200`：`{ userId, account, nickname, createdAt, lastLogin }`

`PATCH /api/users/me`

```json
{ "nickname": "新昵称", "oldPassword": "********", "newPassword": "********" }
```

三个字段均可选；修改密码时必须同时提供 `oldPassword` 与 `newPassword`。`200` 返回更新后的用户信息。

响应体自 R7-5 起多一个 `avatarUrl`：有头像时是 `/api/users/me/avatar`，没有则为 `null`
（见 §3.6）。

### 3.6 头像（R7-5 新增）

`PUT /api/users/me/avatar` —— 请求体为图片二进制，`Content-Type` 取 `image/png` 等六种之一
（与 §5 的图片类型白名单一致）。

`200`：`{ "avatarUrl": "/api/users/me/avatar", "bytes": 20480 }`

- 单张上限 **2MB**，超限 `413 PAYLOAD_TOO_LARGE`；类型不在白名单内 `415 UNSUPPORTED_MEDIA_TYPE`。
- 落盘 `server/data/avatars/{userId}.{ext}`，按 userId 命名，一人一份，换图即覆盖旧文件。

`GET /api/users/me/avatar` → `200` 图片二进制，带 `ETag`；没设置过返回 `404`。

`DELETE /api/users/me/avatar` → `200 { "avatarUrl": null }`，同时删掉磁盘上的文件。

- 头像接口只认**当前登录用户**（`/users/me`），没有 `/users/{userId}/avatar`。
- **前端不能直接 `<img src="/api/users/me/avatar">`** —— 该接口要 `Authorization: Bearer`，
  而 `<img>` 发不出自定义请求头。必须先经接口取二进制再转 object URL
  （实现见 `client/src/features/profile/UserAvatar.tsx`）。

## 4. 文档与内容接口

解析在**客户端**完成（浏览器内按格式分派解析器），服务端负责去重、持久化结构化结果与资源托管。导入分两步，图片按需懒上传。

### 4.1 创建文档（提交元数据与解析结果）

`POST /api/documents`

```json
{
  "fileName": "三体.epub",
  "fileFormat": "EPUB",
  "fileSize": 5242880,
  "contentHash": "sha256:9f2c...",
  "title": "三体",
  "author": "刘慈欣",
  "paragraphs": [
    { "paraIndex": 0, "text": "第一章 科学边界" },
    { "paraIndex": 1, "text": "汪淼站在楼顶……", "sentences": [
        { "sentenceIndex": 0, "startOffset": 0, "endOffset": 12 },
        { "sentenceIndex": 1, "startOffset": 12, "endOffset": 26 }
    ]}
  ],
  "imageRefs": [
    { "imageId": "img_3c81", "paraIndex": 4, "offset": 0, "src": "images/cover.jpg", "alt": "封面" }
  ]
}
```

`201`：`{ "docId": "doc_5b7e", "title": "三体", "paragraphCount": 1204, "imageCount": 37, "importedAt": "..." }`

- 去重：服务端按 `(owner_id, content_hash)` 查重；命中则返回 `409 CONFLICT_DOCUMENT_DUPLICATE` 并在 `details.docId` 给出已存在文档，前端据此提示"该文档已在书架"。
- `imageId` 由**客户端生成 UUID**，作为图片的稳定标识，后续上传与缓存均以它为准。
- 服务端在单个事务内写入 `T_Document`、`T_Paragraph`、`T_Sentence`、`T_ImageResource`（此时 `remote_url` 为空），任一步失败整体回滚。
- 错误：`413 PAYLOAD_TOO_LARGE`、`415 UNSUPPORTED_FORMAT`、`422 PARSE_FAILED`。

### 4.2 上传原始文件

`PUT /api/documents/{docId}/file`，`Content-Type: application/octet-stream`，请求体为文件二进制。

`200`：`{ "docId": "doc_5b7e", "fileUrl": "/api/documents/doc_5b7e/file", "fileSize": 5242880 }`

用途：换设备后无需重新选择本地文件即可重建内容；服务端落盘并回写 `T_Document.resource_url`。若该步骤失败，文档仍保留解析结果，标记为"仅本地可见"（`T_Document.resource_url` 为空），待网络恢复后重试。

`GET /api/documents/{docId}/file` → 返回原始文件二进制（`Content-Type: application/epub+zip` 等）。

### 4.3 上传单张图片（懒上传）

`PUT /api/documents/{docId}/images/{imageId}`，`Content-Type: image/*`，二进制请求体。

`200`：`{ "imageId": "img_3c81", "imageUrl": "/api/documents/doc_5b7e/images/img_3c81", "bytes": 84213 }`

**设计说明**：图片在客户端首次渲染到视口时才上传，与懒加载策略一致，避免导入时一次发出数百张图片的巨型请求。服务端落盘后回写 `T_ImageResource.remote_url`；未上传的图片，其他设备读取时若服务端无副本，则按 `T_ImageResource.src` 回源（若 `src` 为文档内相对路径且无副本，返回 `404 NOT_FOUND`，前端展示"图片不可用"占位）。

### 4.4 书架列表与检索

`GET /api/documents?keyword=三体&category=all&page=1&pageSize=20`

- `category` 取值：`all` 全部书籍、`recent` 最近阅读、`favorite` 已收藏（R7-4 新增）、`bookmarked` 有书签、`offline` 有本地副本。对应书架侧边栏分类。
- `keyword` 匹配标题、作者、正文（正文匹配由服务端在 `T_Paragraph.text` 上执行）。

`200`：

```json
{
  "total": 12, "page": 1, "pageSize": 20,
  "items": [
    { "docId": "doc_5b7e", "title": "三体", "author": "刘慈欣", "fileFormat": "EPUB",
      "coverImageId": "img_3c81", "paragraphCount": 1204,
      "isFavorite": false,
      "progress": { "paragraphIndex": 318, "percent": 0.26, "updatedAt": "..." },
      "bookmarkCount": 3, "importedAt": "..." }
  ]
}
```

### 4.5 文档详情与内容

`GET /api/documents/{docId}` → 元数据 + `paragraphCount` / `imageCount` / `bookmarkCount` / 各设备进度摘要。

`GET /api/documents/{docId}/content?from=0&to=199`

`200`：

```json
{
  "docId": "doc_5b7e", "from": 0, "to": 199, "totalParagraphs": 1204,
  "paragraphs": [ { "paraIndex": 0, "text": "...", "sentences": [ {"sentenceIndex":0,"startOffset":0,"endOffset":12} ] } ],
  "imageRefs": [ { "imageId": "img_3c81", "paraIndex": 4, "offset": 0, "imageUrl": "/api/..." } ]
}
```

响应带 `ETag`；客户端后续请求可发 `If-None-Match`，命中返回 `304`。分段取用是为了避免单行 2000 段落一次传输。

### 4.6 删除文档

`DELETE /api/documents/{docId}` → `204`

级联删除该文档的段落、句子、图片引用、**书签**与**各设备阅读进度**；已上传的原始文件与图片二进制一并清理。此操作不可恢复，前端需二次确认。

### 4.7 收藏（R7-4 新增）

`PUT /api/documents/{docId}/favorite` → `200 { "docId": "doc_5b7e", "isFavorite": true }`

`DELETE /api/documents/{docId}/favorite` → `200 { "docId": "doc_5b7e", "isFavorite": false }`

- 收藏按 `(user_id, doc_id)` 记，落在 `T_Favorite`。
- 两个方向都**幂等**：重复收藏 / 重复取消都返回 `200`，不报 409、不带 `baseVersion`
  —— 收藏没有冲突语义，不并入 §8 的版本机制。
- 非属主文档返回 `403`，不存在返回 `404`。
- 书架列表的每一项带 `isFavorite`（见 §4.4），前端据此点亮书封上的星标。

### 4.8 上传体量上限（R7-4 引入，本次再修订）

- 单次请求体上限：20MB →（R7-4）**100MB** →（本次）**500MB**，
  常量是 `server/src/app.ts` 的 `BODY_LIMIT`。
- `PUT /api/documents/{docId}/file`（§4.2）此前**没有自己的上限**，实际受全局
  `bodyLimit` 约束；R7-4 补上了显式检查（`server/src/routes/resources.ts` 的
  `MAX_FILE_BYTES`），超限返回 `413 PAYLOAD_TOO_LARGE`。
  **两个常量必须同值**：`bodyLimit` 在进 handler 之前生效，若它更小，
  §4.2 的 413 就永远轮不到业务代码发，读者拿到的是 Fastify 那条不带 `details` 的 413。
  测试 `server/test/documents-resources.test.ts` 的「上限一致性」盯着这个等式。
- 前端在**读文件之前**就按同一上限预检（`client/src/features/parse/index.ts`），
  超限直接给中文提示（含实际大小），不把几百 MB 读进内存再失败。
  **跨包无法共享常量，这一处要跟着服务端一起改。**
- 导入相关的两个请求（`POST /api/documents`、`PUT .../file`）超时放宽到 **300 秒**
  （R7-4 是 120 秒，500MB 下不够用），其余请求维持 15 秒。
  服务端没有对应的时限：Fastify 的 `requestTimeout` 默认 0，会把 Node 默认的
  300 秒也一并关掉，所以客户端这一处就是唯一的时限。
- 正文规模仍由 §4.1 的 `MAX_PARAGRAPHS = 20000` 兜底 —— 段落数才是耗内存的那一头。
- ⚠️ **内存风险如实记明**：`bodyLimit` 同时是每请求的内存上限，一个 500MB 的
  `PUT` 就是一份 500MB 常驻内存；前端 `parseEpub` 又是 `await file.arrayBuffer()`
  全量读进内存的，解压后的 DOM、图片 Blob、正文对象与 JSON 字符串会叠加，
  峰值可达文件大小的数倍。演示用的书都在几 MB 量级不会碰到，
  但**数百 MB 的 EPUB 有可能把浏览器的内存打爆**，本项目不做流式/分片改造。

## 5. 图片资源接口（服务端代理）

`GET /api/documents/{docId}/images/{imageId}`

- 成功：`200`，`Content-Type: image/*`，响应头含 `Cache-Control: private, max-age=604800` 与 `ETag`。
- 服务端行为：优先返回本地副本；无副本且 `src` 为外部 URL 时由服务端回源抓取并落盘后返回；仍不可得返回 `404`。
- **安全约束**：回源只允许 `http`/`https` 协议，且**拒绝解析到私有网段/环回地址的目标**（防 SSRF）；单张图片上限 10MB。
- 前端行为：本接口仅由 `IntersectionObserver` 回调在图片进入视口时触发；命中 IndexedDB 缓存则**不发起**该请求；图片离开视口时释放 ObjectURL 并清空内存副本，但保留 IndexedDB 中的 Blob。

## 6. 阅读进度接口

阅读进度为**单值**数据（每设备一行），合并规则见 §8.4。

### 6.1 拉取该文档全部设备的进度

`GET /api/documents/{docId}/progress`

```json
{
  "docId": "doc_5b7e",
  "items": [
    { "progressId": "pg_11", "deviceId": "dev_7a91", "anchor": {"chapterIndex":3,"paragraphIndex":318,"sentenceIndex":41,"charOffset":0,"scrollOffset":1240.5},
      "lastSentenceIndex": 41, "updatedAt": "2026-10-04T11:59:00.000Z", "version": 7,
      "isCurrentDevice": true }
  ]
}
```

返回**该用户该文档的所有设备记录**（而非仅本机），否则新设备拉不到其他设备的进度，跨设备续读无法成立。

### 6.2 上报进度（条件更新）

`PUT /api/documents/{docId}/progress`

```json
{
  "deviceId": "dev_7a91",
  "anchor": { "chapterIndex": 3, "paragraphIndex": 318, "sentenceIndex": 41, "charOffset": 0, "scrollOffset": 1240.5 },
  "lastSentenceIndex": 41,
  "updatedAt": "2026-10-04T11:59:00.000Z",
  "baseVersion": 7
}
```

`200`：

```json
{ "progressId": "pg_11", "version": 8, "updatedAt": "...", "serverReceivedAt": "...", "outcome": "applied" }
```

`409`：冲突信封，`conflict.scope = "progress"`（见 §8.3）。

### 6.3 上报时机（前端约定）

1. 滚动停止 **1500ms** 后（防抖）上报一次；
2. 每次跟读推进到**段落边界**时上报一次；
3. 页面隐藏或卸载时以 `navigator.sendBeacon` 上报最后一次；
4. 以上任一次失败即写入本地待同步队列，由 §8 的批量同步补报。

### 6.4 阅读时长（R7-5 新增）

`POST /api/documents/{docId}/reading-time`

```json
{ "deviceId": "dev_9f2c", "clientId": "b1e7…", "durationMs": 125000,
  "startedAt": "2026-10-12T10:00:00.000Z", "endedAt": "2026-10-12T10:02:05.000Z" }
```

`200`：`{ "docId": "doc_5b7e", "totalMs": 125000 }`

`GET /api/documents/{docId}/reading-time` → `{ docId, totalMs, totalMinutes }`

`GET /api/reading-time/summary` →

```json
{ "totalMs": 7380000, "totalMinutes": 123, "todayMs": 125000, "todayMinutes": 2,
  "weekMs": 3600000, "weekMinutes": 60,
  "books": [ { "docId": "doc_5b7e", "title": "三体", "totalMs": 4200000, "totalMinutes": 70 } ] }
```

- **幂等靠 `clientId`**：`T_ReadingSession` 在 `client_id` 上有唯一索引，落库用
  `INSERT OR IGNORE`，离线队列重发同一条自动变成无操作。`clientId` 由客户端每次上报生成。
- **只统计页面可见且窗口聚焦的时长**，由前端算好再报（`client/src/features/sync/useReadingTime.ts`）。
  单段上限 6 小时，超过判为客户端算错，返回 `400 VALIDATION_FAILED`。
- **不并入 §8**：时长是纯追加型遥测，没有版本号、没有冲突、没有软删除。
  离线队列里的 `readingTime` 条目由阅读界面自己补报（`takePendingProgress` 按 kind 过滤掉了它们）。
- 跨零点的一段按 `startedAt` 归到开始那天，不拆段。

## 7. 书签接口

书签以**客户端生成的 UUID** 为逻辑主键，采用软删除（墓碑），并携带版本号做条件更新。单项接口供书签管理界面（添加/重命名/移动/删除）即时调用；批量同步见 §9。

### 7.1 新增书签

`POST /api/bookmarks`

```json
{ "bookmarkId": "bm_9d2f...", "docId": "doc_5b7e",
  "anchor": { "chapterIndex": 3, "paragraphIndex": 318, "sentenceIndex": 41, "charOffset": 0, "scrollOffset": 1240.5 },
  "name": "到这里", "chapterTitle": "人间词话 · 卷一", "sortOrder": 0,
  "updatedAt": "2026-10-04T12:10:00.000Z" }
```

`chapterTitle`（`string | null`）与 `sortOrder`（`number`）均为**可选**字段：老调用方不传时，
`chapterTitle` 记为 `null`，`sortOrder` 由服务端追加到该文档排序末尾（稠密整数，见 §7.7）。

`201`：`{ "bookmarkId": "bm_9d2f...", "version": 1, "name": "到这里", "sortOrder": 0, "chapterTitle": "人间词话 · 卷一" }`
同一 `bookmarkId` 重复提交（离线重发）时幂等：若已存在且内容相同，返回 `200` 原结果。

### 7.2 重命名 / 移动书签（条件更新）

`PATCH /api/bookmarks/{bookmarkId}`

```json
{ "name": "改个名", "anchor": {...}, "baseVersion": 1, "updatedAt": "2026-10-04T12:12:00.000Z" }
```

`200`：`{ "bookmarkId": "...", "version": 2 }`
`409`：冲突信封，`conflict.scope = "bookmark"`。

### 7.3 删除书签（软删除）

`DELETE /api/bookmarks/{bookmarkId}?baseVersion=2&deviceId=dev_7a91`

`200`：`{ "bookmarkId": "...", "version": 3, "deletedAt": "2026-10-04T12:15:00.000Z" }`
`409`：冲突信封（另一端已修改同一条书签，此时**保留修改、不执行删除**）。
服务端写入 `deleted_at` 墓碑而非物理删除，以便其他设备在增量拉取时获知删除事件。

### 7.4 增量拉取书签

> **本接口只服务增量同步。** 界面上的书签列表请用 §7.5；§7.5 是后加的独立接口，
> 本接口的响应形状保持不变，以免不带分页参数的调用方被 `pageSize` 默认值静默截断。

`GET /api/bookmarks?docId=doc_5b7e&since=2026-10-04T12:00:00.000Z&includeDeleted=true`

```json
{
  "serverTime": "2026-10-04T12:20:00.000Z",
  "items": [
    { "bookmarkId": "bm_9d2f...", "docId": "doc_5b7e", "name": "到这里", "anchor": {...},
      "version": 2, "updatedAt": "...", "deletedAt": null }
  ]
}
```

`since` 为上次成功同步时服务端返回的 `serverTime`；首次拉取省略该参数。`includeDeleted=true` 时一并返回墓碑记录，客户端据此在本地删除。

### 7.5 分页列表（界面列表用）

`GET /api/bookmarks/page?docId=doc_5b7e&sort=order&order=asc&page=1&pageSize=20`

- `sort` 取值 `order`（同文档内拖动顺序，默认）/ `createdAt`（创建时间）/ `chapter`（所属章节）；
  `chapter` 排序时 `chapterTitle` 为空的记录固定排在最后。
- `page` 从 1 起，`pageSize` 默认 20、上限 100。

`200`：

```json
{
  "total": 50, "page": 1, "pageSize": 20,
  "items": [
    { "bookmarkId": "bm_9d2f...", "docId": "doc_5b7e", "name": "人间词话 · 卷一 · 词以境界为最上",
      "anchor": { "chapterIndex": 0, "paragraphIndex": 1, "sentenceIndex": 0, "charOffset": 0, "scrollOffset": 0 },
      "sortOrder": 0, "chapterTitle": "人间词话 · 卷一",
      "version": 1, "createdAt": "...", "updatedAt": "...", "deletedAt": null }
  ]
}
```

### 7.6 跨文档书签总览

`GET /api/bookmarks/overview?page=1&pageSize=20`

**分页作用于文档组**（`total` 为有书签的文档数），组内返回该文档的全部书签，
因此 `bookmarkCount` 是该文档的真实书签总数。

`200`：

```json
{
  "total": 2, "page": 1, "pageSize": 20,
  "groups": [
    { "docId": "doc_5b7e", "docTitle": "人间词话", "bookmarkCount": 2,
      "items": [ { "bookmarkId": "...", "name": "...", "anchor": {...},
                   "sortOrder": 0, "chapterTitle": "人间词话 · 卷一",
                   "createdAt": "...", "updatedAt": "...", "deletedAt": null } ] }
  ]
}
```

### 7.7 拖动排序（整表重排）

`POST /api/bookmarks/reorder`

```json
{ "docId": "doc_5b7e",
  "items": [ { "bookmarkId": "bm_9d2f...", "sortOrder": 0, "baseVersion": 3 },
             { "bookmarkId": "bm_51aa...", "sortOrder": 1, "baseVersion": 1 } ],
  "updatedAt": "2026-10-11T10:00:00.000Z" }
```

`200`：`{ "docId": "doc_5b7e", "applied": 2, "items": [ { "bookmarkId": "...", "sortOrder": 0, "version": 4 } ] }`

`409 SYNC_VERSION_CONFLICT`：任一条 `baseVersion` 不匹配即**整体回滚**（不接受部分成功），
`details.conflict.key` 指出冲突条目，`resolution` 为 `superseded`。

排序位编号策略为**稠密整数 `0,1,2…`**；两端同时拖动的合并规则为 `superseded`（取较新者），
不使用 `keep_both`——否则会为同一条书签造出重复副本。

`400 VALIDATION_FAILED`：`items` 为空 / 存在重复 `bookmarkId` / `sortOrder` 不是整数 / 缺少 `baseVersion` / 缺少 `docId`。
`404 NOT_FOUND`：书签不存在、或不属于当前用户，或不属于给定的 `docId` ——
遵循本文件既有约定（§7.2 / §7.3 的 `!existing || existing.user_id !== userId` 一律返回 `404`）。

## 8. 批量增量同步

`POST /api/sync` — 一次请求完成"上传本地增量 + 拉取服务端增量 + 冲突裁决"，是离线补报的唯一入口。请求头建议携带 `Idempotency-Key`。

### 8.1 请求体（客户端 → 服务端）

```json
{
  "deviceId": "dev_7a91",
  "since": "2026-10-04T12:00:00.000Z",
  "progress": {
    "docId": "doc_5b7e",
    "anchor": { "chapterIndex": 3, "paragraphIndex": 318, "sentenceIndex": 41, "charOffset": 0, "scrollOffset": 1240.5 },
    "lastSentenceIndex": 41,
    "updatedAt": "2026-10-04T11:59:00.000Z",
    "baseVersion": 7
  },
  "bookmarks": {
    "created": [
      { "bookmarkId": "bm_9d2f...", "docId": "doc_5b7e", "anchor": {...},
        "name": "到这里", "updatedAt": "2026-10-04T12:10:00.000Z" }
    ],
    "updated": [
      { "bookmarkId": "bm_51aa...", "name": "改个名", "updatedAt": "2026-10-04T12:12:00.000Z", "baseVersion": 1 }
    ],
    "deleted": [
      { "bookmarkId": "bm_77c2...", "deletedAt": "2026-10-04T12:15:00.000Z", "baseVersion": 2 }
    ]
  }
}
```

字段约定：
- `since`：上次成功同步返回的 `serverTime`；首次同步为 `null`。
- 三个集合均可为空数组；`created` 中的条目必然携带客户端生成的 `bookmarkId`。
- 同一 `bookmarkId` 在一次请求中不得同时出现在 `updated` 与 `deleted` 中（客户端负责归并，取时间戳较晚的一侧）。

### 8.2 响应体（服务端 → 客户端）

```json
{
  "serverTime": "2026-10-04T12:20:03.000Z",
  "applied": {
    "progress": { "version": 8, "outcome": "applied" },
    "bookmarks": { "created": 1, "updated": 1, "deleted": 1 }
  },
  "conflicts": [
    {
      "scope": "bookmark",
      "key": "bm_51aa...",
      "baseVersion": 1,
      "serverVersion": 3,
      "local": { "bookmarkId": "bm_51aa...", "name": "改个名", "anchor": {...}, "updatedAt": "2026-10-04T12:12:00.000Z" },
      "remote": { "bookmarkId": "bm_51aa...", "name": "另一端改的名", "anchor": {...}, "updatedAt": "2026-10-04T12:13:10.000Z" },
      "resolution": "keep_both",
      "resolved": { "bookmarkId": "bm_51aa...", "name": "改个名（此设备）", "version": 4 }
    }
  ],
  "changes": {
    "progress": { "docId": "doc_5b7e", "anchor": {...}, "lastSentenceIndex": 41, "updatedAt": "...", "version": 9, "deviceId": "dev_a310" },
    "bookmarks": {
      "created": [ { "bookmarkId": "bm_c0de...", "docId": "doc_5b7e", "name": "序章", "anchor": {...}, "version": 1, "updatedAt": "..." } ],
      "updated": [ { "bookmarkId": "bm_9d2f...", "name": "新名", "version": 3, "updatedAt": "..." } ],
      "deleted": [ { "bookmarkId": "bm_77c2...", "deletedAt": "..." } ]
    }
  }
}
```

- `applied`：本机增量被接受的统计。
- `conflicts`：本次未静默丢弃的冲突项，逐条给出双方版本与**服务端已落库的裁决结果**（`resolution` 为 `keep_both` 时，`resolved` 即为新增的第二条记录）。
- `changes`：服务端在本机 `since` 之后发生的变更（含其他设备的进度与书签），客户端据此落库。`changes.progress` 为 null 时表示该文档无他端进度。

### 8.3 冲突信封（`SYNC_VERSION_CONFLICT` 的 `details.conflict`）

单项接口（§6.2、§7.2、§7.3）与批量接口（§8.2 的 `conflicts` 数组元素）共用同一结构：

```json
{
  "scope": "progress",
  "key": "doc_5b7e",
  "baseVersion": 7,
  "serverVersion": 9,
  "local": { "...": "本机提交的内容" },
  "remote": { "...": "服务端当前的内容" },
  "resolution": "keep_both",
  "resolved": { "...": "服务端已落库的结果，可为 null（需用户裁决时）" }
}
```

| `resolution` | 触发场景 | 服务端行为 |
|---|---|---|
| `keep_both` | 书签重命名冲突、删除与修改冲突 | 保留双方数据（改名冲突则新增一条同名副本；删改冲突则保留修改、忽略删除），`resolved` 给出落库结果 |
| `require_user_choice` | 无法安全自动裁决 | 不改动数据，`resolved` 为 `null`，等待客户端调用 §8.4 的裁决接口 |
| `superseded` | 进度记录被判定为旧版本 | 保留服务端较新记录，被覆盖的一方**写入冲突记录供读者查看**（不静默丢弃） |

### 8.4 用户裁决接口

`POST /api/sync/resolve`

```json
{ "scope": "bookmark", "key": "bm_51aa...", "conflictAt": "2026-10-04T12:20:03.000Z",
  "choice": "local", "deviceId": "dev_7a91",
  "relatedId": "bm_9f02..." }
```

`choice` 取值 `local` 取本机版本 / `remote` 取云端版本 / `both` 两者都保留。`200` 返回裁决后的记录与新版本号。

`relatedId`：`keep_both` 之后要"二选一"必须知道另一条记录是谁，故为**必填**（取值来自冲突信封的 `resolved.bookmarkId`）。原契约的请求体里没有这个字段，是材料审查 A25 指出的模糊点，实现时补充；仅增字段，向后兼容。

裁决成功后，服务端会把 `T_SyncRecord` 里对应的未决冲突记录置为已解决状态 —— 否则下一次进入阅读页时，§8.6 的拉取接口又会把它读回来重弹一遍。

### 8.5 合并语义（与 §8.3、§8.4 一致）

**书签集合（多值）**

| 情形 | 处理 |
|---|---|
| 两端各自新增（`bookmarkId` 不同） | 并集合并，两端均保留，不构成冲突 |
| 同一 `bookmarkId` 并发重命名 / 移动 | `keep_both`：两份都保留，作为两条记录返回，读者可选其一或全留 |
| 一端删除、另一端修改同一书签 | 保留修改后的书签，不执行删除，并在冲突项标注"该设备曾删除此书签" |
| 两端均删除同一书签 | 幂等，结果一致，不构成冲突 |

**阅读进度（单值）**

1. 取 `updatedAt` 较新者；
2. 施加**不回退保护**：若较新记录的位置早于本机已读位置，保留较前的位置，避免多端切换时进度倒退；
3. 被舍弃的一份以 `resolution: "superseded"` 写入冲突记录，读者可在冲突列表中查看——数据不丢失，但不要求读者在两个进度之间做选择。

**不参与同步的数据**：朗读高亮位置为本地瞬态运行状态，不参与跨端同步，以本机定位为准。本系统不实现操作变换（OT）或无冲突复制数据类型（CRDT）。

**时间戳约定**：`updatedAt` 由客户端提供（离线场景必需）。服务端另记录 `serverReceivedAt` 作为审计与并列时的裁决依据；当双方 `updatedAt` 差值小于 5 秒时，以 `serverReceivedAt` 判定先后，以规避客户端时钟偏移。

### 8.6 拉取未决冲突（迭代轮次 A4 新增）

`GET /api/sync/conflicts?docId={docId}`

`docId` 可选；省略则返回该读者的全部未决冲突。

```json
{ "serverTime": "2026-10-08T06:02:36.073Z",
  "items": [ { "scope": "bookmark", "key": "bm_51aa...", "baseVersion": 1,
               "serverVersion": 2, "local": {}, "remote": {},
               "resolution": "keep_both", "resolved": { "bookmarkId": "bm_9f02..." },
               "note": "两端都改过这条书签，两份都保留了" } ] }
```

`items` 的元素就是 §8.3 的冲突信封，结构完全一致。

**为什么需要它**：§2.2.6 要求"冲突处理中断后未决冲突不得丢失"，而冲突记录虽然写进了 `T_SyncRecord`，界面此前没有读回来的路径 —— 冲突只活在当次会话的内存里，刷新页面即丢。

**返回范围**：只返回**等待读者裁决**的冲突，即 `resolution` 为 `keep_both` 或 `require_user_choice` 的那些。`superseded`（进度冲突）不返回 —— 那是服务端当场按"不回退保护"裁决完毕的，读者无事可做，返回只会让每次打开阅读页都重弹一遍。

**去重**：同一冲突可能被反复检出、每次都落一行记录，本接口按 `scope:key:serverVersion` 去重，只返回最新的一条。

裁决后请调用 §8.4，服务端会把对应记录销账，本接口随即不再返回它。

## 9. TTS 与 AI 伴读代理

前端不直接调用任何第三方服务；服务端按可插拔引擎转发，默认引擎为本地自托管的 Kokoro-FastAPI。

### 9.1 查询可用引擎与音色

`GET /api/tts/engines`

```json
{
  "default": "kokoro-local",
  "engines": [
    { "engine": "kokoro-local", "label": "本地引擎", "available": true,
      "voices": [ { "voice": "zf_xiaobei", "label": "晓北（女）", "lang": "zh" } ] },
    { "engine": "browser-native", "label": "浏览器原生（降级）", "available": true, "voices": [] }
  ]
}
```

`available=false` 的引擎不得出现在前端的可选列表中。

### 9.2 合成单句音频

`POST /api/tts/synthesize`

```json
{ "text": "汪淼站在楼顶，望着远处的城市。", "voice": "zf_xiaobei", "rate": 1.0, "format": "mp3", "engine": "kokoro-local" }
```

`200`：响应体为音频二进制，`Content-Type: audio/mpeg`，响应头 `X-Cache: hit|miss`。

- **缓存键**：`sha256(engine + voice + rate + text)`。服务端与客户端均按此键缓存；客户端命中 IndexedDB 时**不发起**该请求，服务端命中时直接回源文件并置 `X-Cache: hit`。
- 错误：`502 UPSTREAM_TTS_FAILED`（含本地推理服务不可用）、`504 UPSTREAM_TIMEOUT`。前端收到后应降级为浏览器原生 `SpeechSynthesis`；该路径**不经过本接口**，由前端直接调用 Web Speech API，并明确只支持句子级高亮。
- 并发保护：服务端对合成请求排队并限流，超限返回 `429 RATE_LIMITED`。

### 9.3 AI 伴读问答

`POST /api/ai/chat`

```json
{ "docId": "doc_5b7e", "paragraphIndex": 318, "sentenceIndex": 41,
  "question": "这里说的红岸基地是什么？", "history": [ { "role": "user", "content": "..." }, { "role": "assistant", "content": "..." } ] }
```

`200`：`{ "answer": "...", "provider": "deepseek", "usage": { "promptTokens": 812, "completionTokens": 143 } }`

服务端自行拼装"当前段落上下文"，前端不需要上传全文。错误：`502 UPSTREAM_AI_FAILED`、`429 RATE_LIMITED`。本期不实现全文检索与向量检索。

### 9.4 查询音色目录（R7-1 新增）

`GET /api/tts/voices`

与 §9.1 分开，是因为语义不同：§9.1 回答「有哪些**引擎**能用」，这里回答
「本地引擎有哪些**音色**、这台机器装了哪些」。§9.1 的响应结构已定形，故不往里塞。

```json
{
  "engine": "kokoro-local",
  "engineLabel": "本地引擎",
  "engineAvailable": true,
  "voices": [
    { "voice": "zf_xiaobei", "label": "晓北（女·普通话）", "lang": "zh",
      "gender": "female", "chinese": true, "available": true },
    { "voice": "zm_yunxi", "label": "云希（男·普通话）", "lang": "zh",
      "gender": "male", "chinese": true, "available": false, "note": "需安装离线音色包" }
  ]
}
```

- `available=false` 的是**目录里有、本机没装离线音色包**的音色。它们**不是**引擎：
  §9.1「`available=false` 的引擎不得出现在可选列表中」这条**不适用**，前端应当把它们
  置灰列出来 —— 否则读者分不清「这个引擎没这个音色」和「我还没装」。
- `engineAvailable=false` 表示本地推理服务整个没起来。此时目录仍照常返回
  （全部 `available=false`、不带 `note`），由前端决定怎么呈现；
  本地引擎按 §9.1 不进引擎列表，前端把这些置灰音色挂在浏览器原生那条下面，
  读者才知道「装包就能有更好的中文音色」。
- `voice` 字段是 §9.2 缓存键的一部分，**必须与上游 id 逐字节一致**，不得做别名或改写。
- 目录里没有、但上游报了音色（换了模型包之类），服务端会原样补进来。

## 12. 待确认项

1. **内容与图片的传输编码**：本文档假设 JSON 传输解析结果。若单文档段落数接近上限（2000 段），可考虑对 `POST /api/documents` 的请求体做 gzip 压缩（`Content-Encoding: gzip`），需确认是否实施。
2. **书签上限**：未限定单文档书签数量，建议约定上限（如 200 条/文档）并在超出时返回 `400 VALIDATION_FAILED`。
3. **冲突列表的保留期限**：冲突记录长期累积会影响查询性能，需确认清理策略（如 90 天后自动归档）。
4. **伴读对话是否入库**：本文档未定义对话记录的持久化，若需跨设备查看历史需另加接口。
