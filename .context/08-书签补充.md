### 2.3 用例描述（插入 2.2 节，编号 2.2.7）

**用例名：管理书签**

业务目标：读者在阅读过程中对当前位置添加书签，并对已有书签执行重命名、移动与删除；书签在本地持久化并参与跨端同步，使读者在任一设备上均可定位到收藏的位置。

执行者：
主动执行者：读者
被动执行者：云端存储服务（为系统提供书签数据的持久化与版本校验）

前置条件：读者已登录；目标文档已完成解析；读者处于阅读界面或书架界面。

触发条件：读者在阅读界面发起"添加书签"，或在书架"我的书签"分类中发起重命名、移动与删除。

基本交互动作：
1. 读者在阅读界面当前位置发起"添加书签"，可填写书签名称，未填写时以当前章节标题与首句片段作为默认名称。
2. 阅读器视图将文档标识、位置锚点与名称交由书签控制器处理。
3. 书签控制器生成该书签的唯一标识，创建书签实体并写入本地数据库，界面即时反馈"已添加书签"。
4. 书签控制器将该变更写入待同步队列。
5. 读者在书架"我的书签"分类中查看书签列表，对某书签发起重命名，或将其移动到当前阅读位置。
6. 书签控制器按书签标识读取记录，修改名称或位置锚点，递增版本号并写回本地数据库。
7. 读者删除书签时，书签控制器写入删除标记（软删除），本地列表不再显示该书签。
步骤 2～4 为添加流程，步骤 5～6 为重命名／移动流程，步骤 7 为删除流程，三个流程相互独立。

扩展交互动作：
3a. 同一位置已存在名称相同的书签
3a1 书签控制器提示"该位置已有同名书签"，由读者确认后仍以新的唯一标识创建，不覆盖原书签。
5a. 文档已变更导致书签锚点失效（所指向的段落缺失）
5a1 书签控制器保留该书签并在列表中标注"位置已失效"，读者可将其移动至新位置或删除。
7a. 删除时检测到云端该书签已被其他设备修改
7a1 按"同时保留"策略处理：保留修改后的书签、不执行删除，并在冲突列表中标注"该设备曾删除此书签"。

后置条件：书签变更已在本地持久化并写入待同步队列；读者可见的书签列表与本地数据库一致。

非功能需求：
1. 性能：添加、重命名、移动与删除均在本地完成，界面响应时间不超过 100ms；与云端的同步由"跨设备进度同步"用例按增量方式执行，不阻塞本地操作。
2. 可靠性：网络不可用时书签操作仍须成功并保留在待同步队列中，联网后自动补报；操作过程中关闭页面，未同步的书签不得丢失。
3. 业务规则：书签以客户端生成的唯一标识为逻辑主键，不使用服务端自增编号；删除采用软删除，保留删除标记以便其他设备获知删除事件；单文档书签数量不超过 **200** 条；书签操作不得修改文档正文内容。

### 3.4 数据模型增补（修改 4.3.1 节）

原文"设计以下**七张**数据库表"改为"**九张**"（新增书签表与令牌表），并插入书签表定义。字段与接口契约《接口说明文档》第 10 章一致。

```sql
-- 书签表：用户在各文档中收藏的位置
CREATE TABLE T_Bookmark (
  bookmark_id VARCHAR(36)  NOT NULL,          -- 主键，客户端生成的 UUID
  user_id     VARCHAR(36)  NOT NULL,          -- 外键 → T_User
  doc_id      VARCHAR(36)  NOT NULL,          -- 外键 → T_Document
  anchor_json TEXT         NOT NULL,          -- 位置锚点：章节/段落/句子/字符偏移/滚动偏移
  name        VARCHAR(128) NOT NULL,          -- 书签名称
  version     INT          NOT NULL DEFAULT 1,-- 版本号，用于条件更新
  created_at  TIMESTAMP    NOT NULL,
  updated_at  TIMESTAMP    NOT NULL,
  deleted_at  TIMESTAMP    NULL,              -- 软删除墓碑，非空表示已删除
  PRIMARY KEY (bookmark_id)
);

-- 增量同步：按文档与更新时间取变更
CREATE INDEX ix_bookmark_sync  ON T_Bookmark (user_id, doc_id, updated_at);
-- 列表查询：过滤未删除的书签
CREATE INDEX ix_bookmark_alive ON T_Bookmark (user_id, doc_id, deleted_at);
```

设计说明：`bookmark_id` 由客户端生成，使两端各自新增的书签天然具有不同主键，从而可以**并集合并**而不产生冲突；`deleted_at` 采用软删除，使其他设备在增量拉取时能够获知删除事件；`version` 用于服务端的条件更新，受影响行数为 0 即判定为冲突。

### 3.5 数据操作增补（修改 4.3.2 节 `DataAccessLibrary`）

| 接口 | 说明 |
|---|---|
| `boolean insertBookmark(Bookmark)` | 插入新书签；主键冲突时返回 false（由上层按幂等处理） |
| `Bookmark getBookmarkById(bookmarkId)` | 按标识读取单条书签 |
| `List<Bookmark> listBookmarksByDocument(userId, docId, boolean includeDeleted)` | 列出某文档的书签，可选择是否包含墓碑记录 |
| `List<Bookmark> listBookmarksSince(userId, docId, sinceTime, boolean includeDeleted)` | 增量拉取：返回 `updated_at` 晚于 `sinceTime` 的书签变更 |
| `boolean renameBookmark(bookmarkId, name, baseVersion)` | 条件更新：重命名并递增版本号 |
| `boolean moveBookmarkAnchor(bookmarkId, anchorJson, baseVersion)` | 条件更新：修改位置锚点并递增版本号 |
| `boolean markBookmarkDeleted(bookmarkId, deletedAt, baseVersion)` | 条件更新：写入软删除标记并递增版本号 |

### 3.6 用例设计增补（插入 4.1 节，编号 4.1.7）

**"管理书签"用例实现的设计方案**

"管理书签"功能通过控制类 `BookmarkController` 对象完成书签的创建、重命名、移动与软删除，并以实体类 `Bookmark` 保存书签标识、位置锚点、名称、版本号与删除标记。由于书签的增删改查均在本地完成，本用例不直接访问云端存储服务。

读者在阅读界面发起"添加书签"后，`ReaderView` 对象向 `BookmarkController` 对象发消息 `addBookmark(docId, anchor, name)`。`BookmarkController` 对象生成客户端唯一标识，调用实体类 `Bookmark` 对象的 `createBookmark(docId, anchor, name)` 完成构造，并调用 `DataAccessLibrary` 的 `insertBookmark(bookmark)` 写入本地数据库；随后调用 `countBookmarksByDocument(userId, docId)` 校验单文档书签数量上限，超出时提示读者并回滚本次插入。写入成功后向 `ReaderView` 对象返回书签对象，由后者渲染书签标记并提示"已添加书签"，最后调用 `enqueuePendingChange(change)` 将该变更写入待同步队列。

重命名与移动由 `LibraryView` 对象发起：向 `BookmarkController` 对象发消息 `renameBookmark(bookmarkId, name, baseVersion)` 或 `moveBookmark(bookmarkId, anchor, baseVersion)`。`BookmarkController` 对象先调用 `getBookmarkById(bookmarkId)` 读取记录，再调用实体类的 `rename(name)` 或 `moveTo(anchor)`，随后经 `DataAccessLibrary` 执行条件更新；若受影响行数为 0（本地版本已被同步流程改写），则重新读取记录并向界面返回冲突提示。

删除由 `deleteBookmark(bookmarkId, baseVersion)` 触发：`BookmarkController` 对象调用实体类的 `markDeleted(deviceId)` 与 `DataAccessLibrary.markBookmarkDeleted(...)`，写入软删除标记而非物理删除，使其他设备在增量拉取时能够获知删除事件。若服务端返回该书签已被其他设备修改，则按"同时保留"策略处理：保留修改后的书签、不执行删除，并通过 `ConflictDialog` 对象向读者展示"本机删除"与"云端修改"两个版本。

锚点失效的处理：`BookmarkController` 对象在书签列表渲染前调用实体类的 `isAnchorValid(document)` 校验锚点，校验失败的书签仍予保留，仅在列表中标注"位置已失效"，读者可将其移动至新位置或删除。

跨端同步不在本用例内完成：`BookmarkController` 对象只负责将变更写入待同步队列，由"跨设备进度同步"用例的 `SyncController` 对象按增量方式批量提交，并接收服务端返回的书签冲突项（详见接口契约 8.2 节的 `conflicts` 数组）。

## 5. 与既有内容的边界说明

1. **书签与高亮的关系**：本系统不提供为正文段落添加用户高亮的功能。跨端同步的两类数据对象仅为**阅读进度锚点**与**书签集合**；朗读过程中的高亮游标属于本地瞬态运行状态，不参与同步，以本机定位为准。
2. **书签与阅读进度的关系**：阅读进度为单值数据（每设备一行），书签为多值集合。两者的合并规则不同：进度取较新并施加不回退保护，书签按唯一标识并集合并、同一书签冲突时两份保留。两者的共同点是均以版本号实现条件更新。
3. **书签与冲突处理的关系**：书签的冲突由"同步冲突处理"用例统一裁决并展示；`BookmarkController` 只负责本地操作与冲突提示，不自行裁决。
