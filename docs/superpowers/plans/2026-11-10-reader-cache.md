# 阅读与语音缓存实施计划

> 使用 superpowers:executing-plans 在当前工作区执行，最后做独立复核。

**目标：** 按读者已确认的方案完善正文缓存、当前句优先和语音请求合并，不引入 Redis 或其他依赖。

**架构：** 正文使用有容量上限的内存 LRU 和 IndexedDB，缓存解析出的句子以避免重复切分。每次打开仍通过文档详情校验授权和版本。语音继续复用现有文件缓存，增加单飞、异步原子写入；命中缓存不依赖引擎在线。

**约束：** 保留已有未提交修改；不改变锚点和缓存键字节定义；缓存失败必须回退；按 API 地址、读者和文档隔离；播放推进仍由真实结束事件驱动。

- [x] 4. 前后端类型与测试、构建、Chrome 完整回归；比较 17 段与 5000 段重复打开耗时；独立审查并记录边界。

## 关注点

- 切换账号或服务器不能复用另一账号正文。
- 删除后即使存在缓存，也不能继续作为在线有效文档展示。
- 同时打开、StrictMode 重挂载不能重复下载或重复合成。
- 音频格式、音色、语速必须区分，失败不可永久占据单飞槽位。
- IndexedDB 被禁用、容量耗尽、缓存文件损坏时仍能回退。

## 实施记录

- 正文使用内存 LRU 与 IndexedDB JSON 字符串，避免重复下载与切句；缓存损坏回退网络。
- 详情校验和缓存读写之间增加环境快照检查，防止在途切换 API/账号污染旧缓存键，已通过红绿回归。
- 预取 Promise 与前台 Promise 分别标识，预取失败只在可重试错误时切入前台路径，且清理不会删除后继任务，已通过红绿回归。
- 单飞/离线命中/格式隔离测试使用固定上游桩，仅证明缓存编排；真实 Kokoro 在本机不可用，不以桩延迟代替真实合成性能。

- 最终验证：服务端 262 项、客户端 220 项、Chrome 47 项全部通过；类型检查和生产构建通过；独立复核通过。
