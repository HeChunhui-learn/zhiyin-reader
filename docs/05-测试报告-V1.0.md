## 2. 测试方法与分层

分三层，**边界不重叠**：

| 层 | 做法 | 覆盖 |
|---|---|---|
| **单元**（180 例） | 纯函数对拍：与 `node:crypto` 对拍 SHA-256、与手算结果对拍切句与窗口几何 | 解析、切句、缓存键、几何计算 |
| **集成**（237 例） | `app.inject()` 直接打真实路由，断言状态码、错误码、响应体结构、数据库副作用 | 认证、文档、图片、TTS 代理、进度、书签、同步、冲突 |
| **端到端**（43 例） | 真实 Chrome 驱动真实前后端，模拟点击/输入/滚动/多上下文，断言渲染出来的 DOM | 登录、导入、阅读、跟读、书签、设置、跨设备同步、EPUB |

**判定标准**：每条断言必须是二值的（通过 / 失败），不允许"看起来对"。界面类断言一律检查真实 DOM 文本或节点。

### 2.1 为什么 EPUB 放在端到端而不是单元

`client/src/features/parse/epub.ts` 依赖 epub.js，而它的 `section.load()` 需要真实 DOM —— 在 Node 环境里直接跑 `parseEpub` 会**静默挂住**（实测 30 秒超时）。而 `docs/02` 的 D-04 / D-05 / D-06 三个缺陷全是真机才暴露的那一类，用 jsdom 替身去测等于把它们重新盖回去。所以 EPUB 走真实浏览器 + 真实 ZIP + 完整导入链路。

### 2.2 测试隔离

- **单元/集成**：`server/test/setup.ts` 用 `mkdtempSync` 建临时库，`process.env.ZHIYIN_DB` 指过去。**必须在任何业务模块 import 之前设好** —— `server/src/db.ts` 在模块顶层就把 `DB_PATH` 算出来了。
- **端到端**：`server/e2e-server.mjs` 每次启动前重建 `server/data-e2e/`，绝不碰演示库 `server/data/zhiyin.db`。
- **串行**：服务端测试设 `fileParallelism: false`，避免 better-sqlite3 的文件句柄与 WAL 互相绊。

## 5. 发现并修复的缺陷

**本节与 `docs/02` 第 5 节互补。** `docs/02` 记的是 R0–R6 开发中发现的 15 个缺陷（D-01 ~ D-15），本节记的是**集成到 V1.0 之后、由本轮测试新发现的 5 个**（编号 D-T01 ~ D-T05，T = Test）。

### 5.1 缺陷台账

| 编号 | 严重度 | 现象 | 根因 | 本轮处理 |
|---|---|---|---|---|
| **D-T01** | **高** | 两本含同名图片的 EPUB，**第二本导入直接 500**；报错只说"服务端出错了"，指不出原因 | 客户端算 `imageId` 只由 `src + paraIndex` 决定、**不含 docId**；而 `T_ImageResource.image_id` 是**全库主键** | 已用两处用例钉住现状（单元 6 例 + 真机 1 例）；**未修**，修法涉及 schema 与契约，交项目组决策 |
| **D-T02** | 中 | 含 U+2060 的段落，句子 `startOffset`/`endOffset` 与段落文本对不上 → 锚点 `charOffset` 与高亮范围偏移 | 零宽字符表两处实现不一致：`splitSentences.ts` 收了 U+2060，`parse/types.ts` 没收，而前者的注释写着"与后者对齐" | 已钉住差异与后果；**未修** |
| **D-T03** | 低 | 纯标点片段（网文的 `------------` 分隔线）不是"总被丢弃"，而是并入相邻句子 | R9 只在**片段本身**无字母/数字/表意文字时丢弃；`------------` 不含句末标点所以不会被单独切出来 | 已钉住现状；**未修** |
| **D-T04** | 低 | 弯单引号 `’`(U+2019) 被留在下一句开头 | `CLOSERS` 表收了 ASCII `"` 与 `'`，但没收 `’` / `‘` | 已钉住现状；**未修** |
| **D-T05** | 低 | 415 有两个不同错误码 | 请求体没进到路由时（Fastify 内容类型解析阶段拒绝），`code` 是 Fastify 自己的 `FST_ERR_CTP_INVALID_MEDIA_TYPE`，不是 `server/src/errors.ts` 的 `UNSUPPORTED_MEDIA_TYPE` | 已钉住现状；**未修** |

### 5.2 D-T01 详解（最值得修的一个）

**现象（真实浏览器复现）**：读者导入第一本 EPUB 正常；导入第二本**图片路径相同**的 EPUB 时，界面显示服务端的通用错误话术，书没进书架。

**根因链**（两端各自的实现都没有错，拼起来才出问题）：

1. 客户端算 `imageId` 的算法在 `client/src/features/parse/markdown.ts:64`：
   ```
   imageId = `img_${sha256Hex(`${src}#${paraIndex}`).slice(0, 12)}`
   ```
   只由「包内路径 + 段落号」决定，**不含 docId**。那里的注释写明这是刻意的（"同一份文件重复解析结果不变"）。`client/src/features/parse/epub.ts:227` 同口径。
2. 服务端 `server/sql/schema.sql:72` 把它定成**全库主键**：
   ```sql
   image_id   TEXT PRIMARY KEY,
   ```
3. `server/src/routes/documents.ts:217` 直接用客户端给的 `imageId` 入库。

于是两本不同的书，只要都有一张 `/OEBPS/images/cover.jpg` 在第 0 段，第二次导入就报
`SqliteError: UNIQUE constraint failed: T_ImageResource.image_id`，
被统一错误信封兜成 **500 `INTERNAL_ERROR` /「服务端出错了，请稍后重试。」**

**为什么危险**：`images/cover.jpg`、`images/fig1.png` 是 EPUB 里极常见的命名，**一个读者导入两本同源排版的电子书就会踩到**，而报错信息完全指不出原因（前端把它显示成通用错误）。跨读者同样会撞 —— 主键不隔离读者。

**已钉住的位置**：
- `server/test/cross-document-imageid.test.ts`（6 例）—— 含"同 src 算出的 imageId 与 docId 无关"、"第二次导入返回 500"、"跨读者同样撞"、"不传 imageId 走 uuid 兜底则正常"
- `client/e2e/epub-parse.spec.ts` 的最后一条 —— 真实浏览器 + 真实 ZIP 正面复现

> 附带发现：`hashContent`（`client/src/features/parse/index.ts:156-161`）把 `imageRefs` 的 `src` 也算进内容哈希。所以两本书若**正文与图片路径都相同**，会**先**撞导入去重（409 `CONFLICT_DOCUMENT_DUPLICATE`）而走不到 image_id 这一步。真机用例因此让两本正文不同，才能复现到目标缺陷。

**为什么本轮不修**：修法有两条路（`image_id` 改成 `(doc_id, image_id)` 复合主键，或在 imageId 里加 docId 前缀），前者要动 schema（且 `V1.B` 的迁移约定是"仅追加"，改主键属于结构性变更），后者要动 `markdown.ts` 与 `epub.ts` 两处算法并同步契约 §4.1 对 `imageId` 的描述。两者都超出「测试」的范围，属项目组决策。用例已写成"钉住现状"，修好后**把断言反过来**即自然转绿。

### 5.3 D-T02 详解

`.context/02` 的 R7 要求"切分前剔除零宽字符"，两个模块各实现了一份：

| 位置 | 零宽字符表 | 含 U+2060？ |
|---|---|---|
| `client/src/features/parse/types.ts:63`（`normalizeText`） | `[\u200B-\u200F\uFEFF]` | ❌ 否 |
| `client/src/features/readalong/splitSentences.ts:67`（`ZERO_WIDTH`） | `[\u200B-\u200F\u2060\uFEFF]` | ✅ 是 |

后者的注释写着"与 `features/parse/types.ts` 的口径对齐"，**实际没有对齐**。

**后果**：导入时 `normalizeText` 保留 U+2060，切句时 `normalize` 把它删掉，于是句子的 `startOffset` / `endOffset` 是相对**短了一个字符**的串算出来的。段落文本与句子偏移量对不上，锚点的 `charOffset` 与高亮范围会偏移。

**已钉住**：`client/test/readalong-zerowidth.test.ts`（6 例），含一条专门证明"含 U+2060 的段落，句子偏移量与段落文本对不上"。

### 5.4 两处**曾被我误判为缺陷**、实则正确的行为

记录在此，避免后来者重复怀疑：

1. **"过期版本号写入进度不报 409"** —— 实际是我把「同一设备」写成了「换设备」。进度是**每设备一行**（`CLAUDE.md` 同步约定 4），换设备写入只会新建一行，永远不冲突。版本冲突必须发生在同一 `deviceId` 的行上。已按正确语义重写用例（`SY-07` / `SY-08`）。
2. **"进度上报不生效、服务端 items 为空"** —— 实际是**点句子不上报进度**。进度只在 `.reader-scroll` 的 `scroll` 事件里上报（`client/src/pages/ReaderView.tsx:259-281`），防抖 1500ms（`client/src/features/sync/useProgress.ts:19`）。端到端用例因此写了 `scrollReader()` 辅助函数真的滚动。

## 8. 结论与建议

### 8.1 结论

1. **`V1.0-merge` 的集成是成功的**：460 项断言全绿，六项门禁（双端 typecheck / 构建 / 三层测试）全部通过，三个迭代分支与 R7、测试技能已合到一处且互不打架。
2. **测试套件已真正落地**：测试代码进仓库、进 `npm test`、可重复执行。`docs/02` 记录的"252 项断言用临时脚本跑出来、脚本已删除"这一状况**已经结束**。
3. **发现了 1 个高严重度缺陷（D-T01）**：它不在 `docs/02` 的 15 个缺陷之列，且会**在真实使用中直接让第二本同源排版的电子书导不进去**。
4. **演示三项全部有真机证据**：逐句跟读、跨设备同步 + 冲突、图文混排与图片懒加载（含 EPUB 三个历史坑 D-04/D-05/D-06 的回归守卫）。

### 8.2 建议（按优先级）

| 优先级 | 建议 | 理由 |
|---|---|---|
| **P0** | 修 **D-T01**：`T_ImageResource` 改复合主键，或在 `imageId` 里加 docId | 真实使用中会踩到，且报错信息指不出原因。演示若导入两本同源 EPUB 会当场翻车 |
| **P1** | 统一零宽字符表，修 **D-T02** | 影响锚点正确性；且两处不一致本身就是维护隐患 |
| **P1** | 把 `client/e2e` 纳入 CI 门禁 | 端到端最能抓回归（本轮它一次就抓出 D-T01 的真机复现） |
| **P2** | 补 `LibraryView` 的冲突读回 | A4 只做了 `ReaderView`，两边不一致 |
| **P2** | 给 `decode.ts`（GBK）补真机用例 | 该修复有实际用户价值，但目前无回归守卫 |
| **P3** | 引入跨工具覆盖率合并 | 否则客户端覆盖率数字会被长期误读（见 §4.2） |
| **P3** | 决定 `bookmarkName.ts` 的去留 | 合并取舍的遗留物，留着会误导后来者 |

### 8.3 演示前建议手工确认的两件事

自动化测试**不能**替代这两项：

1. **窗口化滚动的观感** —— 几何估算与真实排版总有出入，滚动时是否"跳一下"只有人眼能判断。
2. **真实 Kokoro 音色** —— 若演示机器装了 Kokoro，需人工确认音色与延迟；本报告的所有 TTS 结论都建立在"上游不可用"这一状态下。
