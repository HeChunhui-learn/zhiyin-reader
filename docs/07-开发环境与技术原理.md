## 1. 项目概览

「知音漫卷」是一个跨平台阅读 Web 应用：

- 支持导入 EPUB / TXT / Markdown；
- 图文混排、图片懒加载；
- 逐句高亮跟读（TTS）；
- 阅读进度、书签、阅读时长跨设备同步；
- 电脑浏览器直接使用；
- 手机 / 平板通过 Android APK 安装使用。

总体架构：

```text
                    ┌─────────────────────────────┐
PC 浏览器 ──HTTP──→ │ nginx :80                   │
                    │  ├─ /        → client/dist  │
                    │  └─ /api/    → 127.0.0.1:3000│
                    └──────────────┬──────────────┘
                                   │
                            Fastify + SQLite
                                   ▲
Android 手机/平板 APK              │
(Capacitor WebView, 内置 dist) ────┘

APK 安装包不走服务器：GitHub Releases 托管，服务端代查版本信息
```

> 图中的 nginx 是**部署形态示意**：原演示服务器已停用，本地开发直接用
> `npm run dev`（Vite 5173）代理到 `localhost:3000`，不需要 nginx。

核心思路：**一套 React 代码，两种运行壳；服务端是唯一数据源。**

## 5. 电脑网页端开发原理

### 5.1 构建与部署

开发时：

```text
Vite dev server :5173
  ├─ React 源码（TSX）
  └─ /api 代理 → http://localhost:3000
```

生产构建：

```text
TypeScript → tsc 类型检查
React/TSX → Vite + esbuild 打包
        ↓
client/dist/
  ├─ index.html
  └─ assets/index-*.js / index-*.css
```

上传到服务器后由 nginx 托管：

```nginx
root /opt/zhiyin/app/client/dist;

location ^~ /api/ {
    proxy_pass http://127.0.0.1:3000;
}

location / {
    try_files $uri $uri/ /index.html;
}
```

`try_files` 是 SPA 的关键：`/shelf`、`/read/xxx` 这些前端路由在服务器上并不存在，统一回退到 `index.html`，由 React Router 接管。

### 5.2 浏览器运行链路

```text
打开 http://<服务器地址>
  → nginx 返回 index.html
  → 加载 hashed JS/CSS
  → React 挂载
  → BrowserRouter 解析 /guide、/login、/shelf、/read/:docId
  → 页面通过 /api/* 调后端
```

- **路由**：`BrowserRouter`，地址栏是正常的 `/read/doc_renjian`。
- **接口基址**：默认 `/api`，与页面同源，不需要跨域。
- **认证**：accessToken 只放内存，refreshToken 放 localStorage；401 时自动刷新并重放请求。
- **状态管理**：React 自带 state / context，没有 Redux / Zustand。
- **界面**：桌面优先设计，≥1280px 是原始布局。

### 5.3 阅读器核心原理

1. **解析**：EPUB 用 `epubjs` 只做解析，TXT / Markdown 自研解析，统一成段落 / 句子结构。
2. **渲染**：正文不走 React 差异渲染，而是用 ref + 直接 DOM 操作；逐句高亮只改对应节点的 class。
3. **长文档窗口化**：超过 150 段才启用，只渲染视口上下各一屏，其余用撑高块占位。
4. **图片懒加载**：`IntersectionObserver` 进入视口才取图；图片缓存进 IndexedDB。
5. **进度与书签**：滚动时计算锚点（章节 / 段落 / 句 / 字符 / 滚动偏移），上报服务端；离线先写待同步队列。

### 5.4 离线与同步

- IndexedDB 分四个 store：图片、音频、待同步队列、阅读背景。
- 断网时进度 / 书签写 `pending` 队列，联网后批量调 `POST /api/sync` 补报。
- 服务端是唯一事实来源；书签用版本号 + 软删除墓碑，进度按 `deviceId` 分行，冲突可保留两份。
- 每台设备有独立 `deviceId`，避免手机覆盖电脑的滚动位置。

## 6. 手机 / 平板端开发原理

### 6.1 为什么用 Capacitor，而不是重写 Android

项目需要：

- 同一套界面和业务逻辑；
- 能安装成 APK；
- 能调用文件选择、WebView、系统 TTS 等原生能力；
- 开发成本低。

Capacitor 的方案：

```text
React 构建产物 dist
      ↓ npx cap sync android
APK 内置 assets/public/
      ↓
Android 系统 WebView 加载本地页面
      ↓
JS ↔ 原生桥（Capacitor Bridge）
```

手机端本质是 **「WebView 壳 + 本地前端资源 + 原生桥」**，不是 Kotlin 重写。

### 6.2 APK 构建链路

APK 不再在本机构建、也不手工上传，而是**推 tag 由 GitHub Actions 出包并发布 Release**（工作流见 `.github/workflows/android.yml`）：

```text
git tag v1.9.0 && git push origin v1.9.0
      ↓
GitHub Actions（ubuntu-latest，JDK 21，Gradle 8.14.3，Android SDK 36）
      ├─ 从 tag 算出 versionName=1.9.0 / versionCode=10900
      ├─ 前端构建注入 VITE_API_BASE / VITE_APP_VERSION_CODE
      ├─ npx cap sync android
      ├─ gradle :app:assembleRelease（用 Secrets 里的 keystore 签名）
      └─ gh release create v1.9.0，附件固定命名 zhiyin.apk
```

版本号规则只有一条：**tag 是唯一事实来源**。

| tag | versionName | versionCode |
|---|---|---|
| `v1.9.0` | 1.9.0 | 10900 |
| `v1.10.2` | 1.10.2 | 11002 |

`versionCode = 主 * 10000 + 次 * 100 + 修订`，保证单调递增（旧包的 versionCode 是 9）。

本机手工构建仍然可以，用于调试：

```bash
cd client
VITE_API_BASE=http://192.168.1.5:3000/api npm run build
npx cap sync android
cd android
JAVA_HOME='C:\Program Files\Android\Android Studio\jbr' ./gradlew assembleRelease
```

> 本机必须用 **JDK 21**：`capacitor.build.gradle` 里 source/targetCompatibility 都是 `VERSION_21`，JDK 17 会直接编译失败。
> 本机不打 tag 时 versionCode 取 10、versionName 取 1.9.0（`build.gradle` 的默认值），只能自测，不能当正式发布包。

产出：

```text
app-release.apk
包名 com.zhiyin.reader
minSdk 24 / targetSdk 36
```

`webDir: 'dist'` 会把整个前端拷进 `android/app/src/main/assets/public`，所以 **App 启动不依赖网络**；书籍数据仍需请求服务器（已缓存的图片 / 音频可离线看）。

### 6.3 与电脑端的三个关键差异

| 差异 | 电脑网页端 | 手机 / 平板 APK | 原因 |
|---|---|---|---|
| 路由 | `BrowserRouter` | `HashRouter` | WebView 从本地 assets 取页面，没有 nginx 的 SPA 回退；刷新 `/read/xxx` 会 404，Hash 路由永远是 `index.html` |
| API 地址 | 同源 `/api` | 绝对地址（`VITE_API_BASE` 打进去的默认值） | WebView 的 `/api` 会打到 `localhost` 自己身上 |
| 跨域 / 明文 | 同源，无跨域 | 跨域 + HTTP | 服务端 CORS 反射 `http://localhost`；Android Manifest 开 `usesCleartextTraffic` |

源码里通过 `isNativeApp()` 判断运行环境：

```ts
const Router = isNativeApp() ? HashRouter : BrowserRouter
```

`capacitor.config.ts` 里 `androidScheme: 'http'` 也是有意的：服务器目前只有 HTTP，如果 WebView 跑在 `https://localhost`，请求 HTTP 接口会被当混合内容拦截。

**服务器地址可在运行时改**：打包写死的只是默认值，登录页与个人主页各有一个「服务器地址」入口
（组件 `client/src/features/app/ServerSettings.tsx`），改完存 `localStorage`（键 `zhiyin.apiBase`），
下次启动直接生效，不必重新打包。这是服务器迁移或下线后，老安装包唯一的自救办法。

### 6.4 手机 / 平板布局原理

同一份 CSS，用断点覆盖桌面样式：

| 断点 | 设备 | 主要变化 |
|---|---|---|
| `≥1280px` | 桌面 | 原始设计，不做覆盖 |
| `768–1279px` | 平板 | 书架 3 列；侧栏收窄；阅读页顶栏 / 播放条允许换行 |
| `<768px` | 手机 | 书架 2 列；左侧栏变横向滑动分类条；登录页上下排；播放条换行；隐藏昵称等次要元素 |

另外：

- `viewport` 改为 `width=device-width, viewport-fit=cover`；
- 用 `env(safe-area-inset-*)` 让出刘海 / 圆角屏；
- 触摸设备没有 hover，按钮和点击区域按手指尺寸调整；
- 平板不是单独一套代码，而是同一个 APK 走 768–1279 断点。

### 6.5 原生壳的版本与更新

- 原生 App 发请求时带 `X-App-Version-Code`（值来自构建时注入的 `VITE_APP_VERSION_CODE`）；
- 旧版本会被服务端返回 `426 APP_UPDATE_REQUIRED`；
- 原生壳里的 `UpdateGate` 弹出不可关闭的更新弹窗，引导下载新 APK；
- 更新源是 **GitHub Releases**：服务端 `GET /api/app/version` 代查 GitHub API（缓存 5 分钟）
  再下发版本号与下载地址，见 `server/src/routes/appVersion.ts`；
- 网页版没有 APK 概念，改用 `WebUpdateBanner` 比较 `index.html` 里的 `zhiyin-build`，提示「立即刷新」。

## 8. 语音朗读原理

### 8.1 一句话原理

朗读不是把整篇文章丢给 TTS，而是：

```text
前端把正文切成句子
  → 逐句交给某个引擎合成 / 发声
  → 这一句播完（ended / onDone / onend）
  → 游标 +1，高亮下一句
  → 同时预取后面几句，减少句间停顿
```

核心约束：**念完一句才推进游标**。所以高亮位置和声音是对应的，不是用定时器假推进。

### 8.2 整体流程

```text
ReaderView
  ├─ splitSentences()          把段落切成句子
  ├─ useReadAlong()            播放循环、游标、预取、错误处理
  │     └─ TtsEngine.speak(句子)
  │           ├─ ServerTtsEngine   → 服务端 Edge TTS → 音频 Blob → <audio>
  │           ├─ NativeTtsEngine   → Android 系统 TextToSpeech
  │           └─ BrowserTtsEngine  → 浏览器 speechSynthesis
  └─ cursor 变化 → 高亮 .sent-active + 自动滚动 + 上报阅读进度
```

播放循环会先 `preload` 后面 2–3 句，再 `speak` 当前句；合成与播放并行，避免“每句停一下”。

### 8.3 服务端 Edge TTS（PC / 手机主路径）

调用链：

```text
客户端 ServerTtsEngine
  → POST /api/tts/synthesize
      { text, voice, rate, engine: "edge-tts" }
  → Fastify 校验 JWT、文本长度、语速、音色
  → EdgeTtsProvider
  → 微软 Edge 在线语音
  → MP3 音频
  → 返回给客户端
  → <audio> 播放，ended 后推进下一句
```

关键点：

- 前端**不直接**访问微软服务，统一经服务端代理；第三方密钥不会出现在前端。
- 服务端当前 `TTS_PROVIDER=edge`，使用 `@andresaya/edge-tts`；默认有 14 个中文音色，默认「晓晓」。
- Edge TTS 不需要 API Key，但服务器必须能访问外网。
- 单句最长 500 字；语速 0.5–2.0，服务端换算成 Edge 的 `-50% ~ +100%`。
- 服务端并发上限 2，排队上限 8，超时 20 秒；排队满返回 429。
- 服务端可选本地 Kokoro-FastAPI（OpenAI 兼容），未设置 `TTS_PROVIDER=edge` 时默认走它。

两级缓存：

```text
客户端 IndexedDB 音频缓存
        │ 命中 → 直接播，不发请求
        ▼ 未命中
服务端磁盘缓存 server/data/tts/<hash>.mp3
        │ 命中 → 直接返回，X-Cache: hit
        ▼ 未命中
调用 Edge TTS 合成 → 写磁盘 → 返回
```

缓存键两端必须完全一致：

```text
sha256(engine \u0001 voice \u0001 rate \u0001 text)
```

所以同一句话、同一音色、同一语速，第二次朗读几乎零延迟；换引擎 / 音色 / 语速会重新合成。

### 8.4 设备原生降级（两端实现不同）

#### PC：浏览器原生（Web Speech API）

```text
BrowserTtsEngine
  → window.speechSynthesis
  → new SpeechSynthesisUtterance(text)
  → u.lang = 'zh-CN'
  → u.voice = 系统中文嗓音
  → speechSynthesis.speak(u)
  → onend 触发，推进游标
```

特点：

- 底层调用 Windows 的 SAPI / 系统语音，例如 Microsoft Huihui。
- 不需要网络，但音色取决于电脑装了什么。
- **没有真实音频文件**，拿不到字级时间戳，只能做**句子级高亮**。
- Chrome 偶发吞掉 `start/end` 事件，代码里加了看门狗和重试。

#### Android 手机 / 平板：系统 TextToSpeech

Android WebView **不实现 Web Speech API**，`window.speechSynthesis` 是 `undefined`。所以不能照搬 PC 的浏览器降级，而是走 Capacitor 插件：

```text
NativeTtsEngine
  → @capacitor-community/text-to-speech
  → Android 系统 TextToSpeech
  → TextToSpeech.getSupportedVoices() 取中文音色
  → TextToSpeech.speak({ text, lang, rate, voice })
  → onDone 后 resolve，推进游标
```

特点：

- 调用手机系统自带的 TTS 引擎（Google TTS、三星 / 小米等厂商引擎）。
- 需要系统里装有中文语音包；没有中文音色时该引擎不会出现在列表里。
- 完全离线可用，不经过服务器。
- 没有音频 Blob，不能缓存、不能预取，只有句子级高亮。
- 平板上是同一个 APK、同一个引擎，只是布局走平板断点。

#### 为什么两端降级路径不同

| 运行容器 | 有没有 `speechSynthesis` | 降级方案 |
|---|---|---|
| PC Chrome / Edge | 有 | 浏览器原生 Web Speech |
| Android WebView（APK） | **没有** | Capacitor 原生 TTS 插件 → 系统 TextToSpeech |

应用里会看到两个不同的降级引擎名：

```text
浏览器原生（降级）      ← PC
设备原生（降级）        ← Android
```

### 8.5 引擎选择与降级顺序

启动阅读页时，`loadEngines()` 会同时做四件事：

1. 请求 `/api/tts/engines` 和 `/api/tts/voices`；
2. 等浏览器嗓音列表就绪（最多 800ms）；
3. Android 壳里读取系统 TTS 中文音色；
4. 合并成可选引擎列表。

选择顺序：

```text
服务端引擎（edge-tts）可用 → 默认用它
        ↓ 服务端不可用
Android：设备原生 TTS
PC：   浏览器原生 TTS
        ↓ 都没有
显示“当前环境不可用”，点跟读时给出明确提示
```

用户可以在播放条里手动切换引擎和音色，选择会记在 localStorage，下次进阅读页继续用。播放中服务端合成失败会停止当前朗读并提示，用户可切换到设备原生 / 浏览器原生。

### 8.6 局限与注意

1. **所有路径都是句子级高亮**，不是逐字高亮；服务端 Edge 返回的是整句音频，没有字级时间戳。
2. **Edge TTS 是在线服务**，服务器断网或微软侧波动会导致合成失败。
3. **设备原生音色因机型而异**，同一句话在不同手机上可能听起来不同。
4. **Android 系统没有中文 TTS 包**时，设备原生引擎不可用；此时只能依赖服务端 Edge TTS。
5. 服务端缓存和客户端缓存键必须保持一致，否则每句都会重新合成。

## 9. 关键设计决策

| 决策 | 说明 |
|---|---|
| 一套代码，两种壳 | 避免 Web / Android 双端重写；PC 用浏览器，手机用 Capacitor WebView |
| 服务端为唯一事实来源 | 手机和电脑不直接互传；书籍、书签、进度都由服务端统一管理 |
| 核心逻辑纯 TypeScript | 解析、句子切分、同步、TTS 调度与 React 解耦，便于单测 |
| 正文直接 DOM + 窗口化 | 长文档不触发 React 差异渲染；超过 150 段只渲染视口附近 |
| 离线优先 | IndexedDB 缓存 + 待同步队列，联网后补报 |
| 第三方密钥只在服务端 | TTS 等外部服务统一经 `/api/*` 代理 |
| 移动端不重写原生 | Capacitor 壳 + 响应式 CSS，换取开发效率和一致性 |

## 10. 当前限制与后续工作

- **HTTP，无 HTTPS / 域名 / ICP 备案**：目前仅适合答辩演示，正式对外需要补齐。
- **Edge TTS 依赖在线服务**：可切换本地 Kokoro 或云 TTS 作为备选。
- **句子级高亮**：尚未实现字级时间戳对齐。
- **SQLite 单机**：适合课程项目；并发量上升可迁移 PostgreSQL。
- **没有 ESLint / Prettier**：依赖 TypeScript 类型检查与团队约定。
- **当前部署未使用 Docker**：直接 nginx + systemd 原生运行。
- **AI 伴读（DeepSeek）**：技术选型中有规划，当前版本未实现，不应写成已完成功能。
- **Android 真机 TTS 差异**：需要按具体机型确认中文语音包与音色可用性。
