多端适配方案

把现在只跑桌面的阅读器，做成手机、平板、桌面三端都能用的东西： 走哪条路、会撞上什么、按什么顺序做。

现状 React 18 + Vite + Fastify + SQLite，纯 CSS 约束 不引 UI 库，四人并行开发中

不要用 React Native 或 Flutter 重写。

阅读器整套是「ref + 直接操作 DOM + 实测高度回写几何表」的窗口化渲染，原生框架里没有等价物—— 重写等于把最难的部分从零做一遍。推荐响应式 Web + PWA 打底， 真需要「装到手机上的应用」再套 Capacitor。两条路都保留现有代码，桌面端顺带受益。

三条路线

路线 保留现有代码 能进应用商店 主要代价
响应式 Web + PWA 100% 否（可「添加到主屏」） 改 CSS 与触摸交互，工作量中等
Capacitor 套壳 约 95% 是 要装 Xcode / Android Studio，要签名
原生重写 0% 是 阅读器要重做，不划算

动手前必须先定两件事

这两件不定，后面全白干。

  • 要「能装到手机上的应用」还是「能在手机上打开的网页」

    直接决定要不要引入 Capacitor 那一整套原生工具链。

  • 手机上的数据从哪来

    前端所有请求打 /api，开发时靠 Vite 代理转发到 localhost:3000。 手机装上之后没有 Vite 代理了，必须有一个真实可达的 API 地址。

    三条路：局域网 IP（演示够用，但要同一 WiFi）、部署到公网机器、或把 SQLite 搬到设备本地 （那等于换架构，工作量大得多）。

这个项目特有的拦路石

以下是实际查出来的，不是通用建议。

  • 两行代码就把手机彻底挡住了

    client/index.html 里 <meta name="viewport" content="width=1280">， 以及 app.css:87 的 body { min-width: 1024px }。

    前者让手机浏览器按 1280 宽渲染再整体缩小，字小到看不清。这两行不改，后面全白干。

  • 全项目 0 个 @media 查询

    app.css 1751 行，一个断点都没有。要补的固定宽度：

    位置现在手机上要变成
    .guide-stage880px撑满减内边距
    .login-pagegrid 45% / 55%单栏，品牌区缩成顶部一条
    .book-gridrepeat(4, 1fr)2 列 / 1 列
    .reader-contentmax-width 720px撑满（见下一条）
    .toc-panel 抽屉260 / 280 / 300px底部弹出或全屏
    .modal640px撑满

  • 阅读器的几何表——这里最需要小心

    buildGeometry(paragraphs, fontSize) 按栏宽 720px、字号 16px → 一行 42 字估算每段高度。 手机上栏宽变成 360px 时，这个假设立刻失效。

    • 已经渲染出来的段落会实测回写，所以会自愈
    • 还没渲染到的段落仍按旧栏宽估 → 滚动条长度和跳转落点会偏，直到滚过去
    • 更麻烦的是视口高度变化：地址栏收起、横竖屏切换、软键盘弹出，都会让窗口算错

    好消息：处理「改字号」时已经解决过同一类问题（重建几何表 + 按当前段落重锚定）。 旋转、栏宽变化是同一个模式，把 (fontSize) 扩成 (fontSize, columnWidth) 再加一个 ResizeObserver 触发即可。不要另起一套。

  • 触摸屏没有 hover、没有 Esc、没有右键

    • 关抽屉现在靠 Esc → 要改成手势 / 返回键（点遮罩关闭已经有了）
    • title="…" 提示在触摸上根本不显示，例如书签按钮上「将命名为…」、音色下拉的说明
    • 卡片上的删除 / 收藏按钮默认 opacity: 0.55——触摸下仍然可见，只是不会变亮。不算阻塞，建议改成常亮
    • 播放条按钮最小点击区只有 22–28px，规范建议 ≥44px

  • 移动端存储会被系统清掉

    iOS Safari 对未添加到主屏的站点，7 天不用会清掉 IndexedDB / localStorage。

    影响图片缓存、音频缓存、阅读偏好——最要紧的是离线待同步队列（pendingQueue）会被清空， 等于未同步的改动丢失。书签和进度在服务端，没事。PWA 装到主屏或 Capacitor 打包都能规避。

  • TTS 在移动端的两点

    • 服务端 Kokoro 这条路不变，但手机得能连到跑 Kokoro 那台机器的 8880
    • iOS 上 speechSynthesis 要求用户手势触发，首次 getVoices() 常返回空。 现有代码已处理 voiceschanged，但「必须点一下才发声」要在真机上确认
    • 后台播放与锁屏控制 Web 层做不到，要 Capacitor 插件

分阶段步骤

六个阶段有真实先后关系（阶段 0 不定，后面都是白干），所以按序编号。

  1. 阶段 0

    先定两件事 不占工期

    要能安装的应用还是能打开的网页？手机的数据从哪来？

  2. 阶段 1

    响应式地基 1–2 天

    • viewport 改成 width=device-width, initial-scale=1
    • 去掉 body { min-width: 1024px }，改成三档断点：手机 <768 / 平板 768–1279 / 桌面 ≥1280
    • 按上表把固定宽度改成流式

    验收：iPhone SE（375px）与 iPad（1024px）上都不出现横向滚动条。

  3. 阶段 2

    阅读器适配——最难的一段 2–3 天

    • 几何表参数化扩成 (fontSize, columnWidth)，复用已有的重锚定逻辑
    • 加 ResizeObserver / orientationchange 触发器
    • 播放条换成触屏友好的大按钮，目录与设置抽屉改成底部弹出

    验收：手机上滚动不卡；旋转后不跳章；跟读高亮位置仍然正确。

  4. 阶段 3

    触摸交互 1 天

    • 去掉对 hover 与 Esc 的依赖，点按目标 ≥44×44
    • 把 title 提示改成可见文案
  5. 阶段 4

    PWA 1 天

    • manifest.json + service worker：可安装、离线打开书架
    • 图标、启动图、主题色

    验收：手机浏览器「添加到主屏幕」后能独立窗口打开，断网也能进书架。

  6. 阶段 5

    Capacitor 打包 按需，2–3 天

    • @capacitor/core · cli · ios · android
    • 原生插件替换：文件系统（替掉大 IndexedDB）、TTS（后台播放）
    • 需要 Xcode / Android Studio 与开发者签名
  7. 阶段 6

    服务端部署 按需

    把 Fastify + SQLite 部署到手机能访问的机器上。

工期，以及几句实话

全部做完是 1–2 周的活，不是两三天。其中阶段 2 占一半以上。

  • 阶段 1 可以先做，收益立刻可见

    桌面端窄窗口的体验也会变好，而且不改任何业务逻辑，风险低。

  • 阶段 2 动手之前先补测试

    D 同学刚落地了 460 例测试（还没 npm install）。 阅读器的几何回写是最容易改坏、又最难发现的地方——「跳转落点偏几百像素」这种 bug 不报错。 有回归网再动它，安全得多。

  • 别一次改完再验

    按项目一贯做法，一个阶段一个阶段来，每步停下来验证。

  • 手机上的混排与跟读比桌面难

    小屏一屏放不了几句，高亮和自动滚动的观感要重新调，不能直接照搬桌面的参数。

  • 这件事跟现有约定冲突，要先改约定

    CLAUDE.md 第六节明写着不做移动端 / 平板适配与响应式断点。 现在是四人并行迭代，动这条之前先改约定、并且跟组里说一声，否则合并时会打架。
