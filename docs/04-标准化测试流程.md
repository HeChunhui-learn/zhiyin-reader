# 知音漫卷 标准化测试流程

软件工程课程设计 · 第一组
适用分支：`V1.0-merge`（= `main` + `V1.A` + `V1.B` + `V1.C` + `V1.D`）
本文回答一个问题：**在这个仓库里，怎么把测试跑起来，以及为什么是这么跑的。**

> 配套文档：`docs/05-测试报告-V1.0.md`（本轮实测结果与缺陷台账）。
> 本文讲流程与规范，那份讲结论。两份都以 `docs/test-evidence.log` 的原始输出为准。

---

## 1. 为什么要建这套流程

`AGENTS.md` 的「测试现状」一节把问题说得很清楚，这里直接引用其要点：

- **仓库里没有任何测试文件**，`package.json` 里也**没有 test 脚本**
- `docs/02-测试用例与测试报告.md` 里的 **252 项断言是用临时脚本跑出来的，脚本已删除**
- 测试套件的正式归属是「角色 D 的 D2」（`V1.B` 计划文档的 Global Constraints），**一直没落地**
- 因此当时每个任务的验证方式是「可复现的验证命令 + 预期输出」替代红绿循环

**没有测试的代价是具体的**：`docs/02` 记的 15 个缺陷里，D-11（两端改同一书签根本不触发冲突）与 D-12（只改名会把书签位置冲成第 0 段）**都不报错**，只是行为悄悄不对。这类缺陷只能靠可重复执行的断言守住，靠人工验证迟早会漏。

本轮把 D2 落地了：**测试代码进仓库、进 `npm test`、可重复跑**。

## 2. 测试分层

三层，各管一段，**不重叠**：

| 层 | 工具 | 位置 | 覆盖什么 | 本轮数量 |
|---|---|---|---|---|
| 单元 | Vitest | `client/test/` | 纯函数：解析、切句、缓存键、窗口几何 | 180 |
| 集成（接口） | Vitest + `app.inject()` | `server/test/` | 真实路由：状态码、错误码、响应体、数据库副作用 | 237 |
| 端到端 | Playwright + 真实 Chrome | `client/e2e/` | 真实浏览器：排版、CSS、滚动、点击、多上下文同步 | 43 |
| | | | **合计** | **460** |

### 分层边界（重要，别越界）

- **单元层刻意不用 jsdom。** `client/vitest.config.ts` 是 `environment: 'node'`。需要浏览器 API 的东西（IndexedDB、IntersectionObserver、SpeechSynthesis）**交给 Playwright**，不用替身硬凑 —— 替身跑通了不代表真机跑得通，反而会给出虚假的绿。
- **接口层不监听端口。** 全部走 `app.inject()`（`server/test/helpers.ts` 的 `makeApp()`）。测试跑起来的时候，开发用的 3000 端口可能正被 `npm run server` 占着。
- **EPUB 解析放在端到端。** `client/src/features/parse/epub.ts` 依赖 epub.js，而它的 `section.load()` 需要真实 DOM —— 在 Node 里跑会**静默挂住**（实测 30s 超时）。而 `docs/02` 的 D-04/D-05/D-06 三个缺陷全是真机才暴露的那一类，用替身测等于把它们重新盖回去。所以 EPUB 走 `client/e2e/epub-parse.spec.ts`。

## 4. 怎么跑（六步）

在 `zhiyin-reader/` 根目录，按顺序：

```bash
# [1] 服务端类型检查
cd server && npm run typecheck

# [2] 前端类型检查
cd client && npx tsc --noEmit

# [3] 前端生产构建（提交前必须过）
cd client && npm run build

# [4] 服务端接口与集成测试（237 例）
cd server && npm test

# [5] 客户端单元测试（180 例）
cd client && npm test

# [6] 端到端测试（43 例，真实浏览器）
cd client && npx playwright test
```

**首次运行的前置**（只做一次）：

```bash
cd server && npm install
cd client && npm install
cd server && npm run seed          # 建库 + 灌演示数据（端到端会另建自己的库）
```

### 一次跑完全部的辅助命令

```bash
# 服务端 + 客户端单元/集成
cd server && npm test && cd ../client && npm test
```

### 开发时常用的变体

| 命令 | 作用 |
|---|---|
| `cd server && npm run test:watch` | 服务端测试 watch 模式 |
| `cd client && npm run test:watch` | 客户端测试 watch 模式 |
| `cd server && npm run test:coverage` | 只跑服务端并出覆盖率 |
| `cd client && npm run test:coverage` | 只跑客户端并出覆盖率 |
| `cd client && npx playwright test --ui` | 端到端交互式调试 |
| `cd client && npx playwright test ui-flows` | 只跑某个 spec |
| `cd client && npx playwright test -g "EPUB"` | 按用例名过滤 |

## 5. 隔离规范（三个"绝不能用演示库"）

### 5.1 单元/集成：每文件一个临时库

`server/test/setup.ts` 用 `mkdtempSync` 建临时目录，把 `process.env.ZHIYIN_DB` 指过去。

> ⚠️ **必须在任何业务模块被 import 之前设好。** `server/src/db.ts` 在模块顶层就把 `DB_PATH` 算出来了（`process.env.ZHIYIN_DB ?? ...`），之后再改环境变量不会生效。`setupFiles` 保证在任何测试文件 import 之前执行；`setup.ts` 本身只碰 `node:` 内置模块，就是为了守住这个顺序。

不共用 `server/data/zhiyin.db` 的理由：用例会写书签、删文档、改密码，跑一遍就把演示库搞脏了，演示前还得记得重建。

### 5.2 端到端：独立的 `server/data-e2e/`

`server/e2e-server.mjs` 每次启动前 `rmSync('server/data-e2e')` 并重建种子数据，通过 `ZHIYIN_DB` 指过去。端到端会反复导入文档、改书签、删文档，绝不能拿演示库跑。

> 注意：图片／原始文件／头像仍落在 `server/data/` —— 那几个目录的路径由 `server/src/db.ts` 的 `SERVER_ROOT` 决定，不走 `ZHIYIN_DB`。端到端用例不碰它们，所以实际上不会写什么。

### 5.3 服务端测试串行跑

`server/vitest.config.ts` 设了 `fileParallelism: false`。理由：`better-sqlite3` 的文件句柄与 WAL 在并发下会互相绊。

## 6. 写用例的约定

### 6.1 用例编号对齐 `docs/02`

断言里带 `docs/02` 的用例编号（`AU-04`、`SY-17`、`VD-07`…），这样两个文档能互相对照：

```ts
it('AU-06 ★ 不存在的账号与密码错误返回**同一个**错误码（防用户枚举）', async () => { ... })
it('SY-08 不回退保护：时间更新但位置更靠前的一方被拒', async () => { ... })
```

### 6.2 只断言二进制结果

判定标准是「每条断言必须是二值的」。不允许"看起来对"。界面类断言一律检查真实 DOM 文本或节点，不断言"调用过某个函数"。

### 6.3 跨包一致性用对拍

`client/test/tts-cachekey-parity.test.ts` 直接 `import` 服务端那份实现，把「改一边必须改另一边」这条约定变成可执行的守卫：

```ts
import { ttsCacheKey as clientKey } from '../src/features/readalong/ttsCacheKey'
import { ttsCacheKey as serverKey } from '../../server/src/tts/cacheKey'
```

不一致的后果是**静默**的：客户端永远命中不了服务端缓存，每句都重新合成，界面上只是"变慢了"，不会有任何报错。

### 6.4 缺陷写成"钉住现状"的用例

发现产品缺陷但**本轮不该改**（比如涉及 schema 或接口契约）时，把当前行为如实断言下来，并在注释里写清机制与修法：

```ts
// 现状：撞 T_ImageResource.image_id 主键 → 统一错误信封兜成 500
expect(second.statusCode).toBe(500)
```

好处有两条：缺陷不会因为"没记录"而被忘掉；修好之后**把断言反过来**就自然转绿，不用重新设计用例。

### 6.5 注释写"为什么"

仓库现有的风格是「注释说明为什么这么做」。测试里的注释尤其要写清**为什么要这么测**：是守着哪个已修复的缺陷（`D-04`）、还是哪个反直觉的行为（进度只在 scroll 事件里上报）。

## 7. 端到端的环境要求

### 7.1 用本机 Chrome

`client/playwright.config.ts` 里是：

```ts
projects: [{ name: 'chromium', use: { ...devices['Desktop Chrome'], channel: 'chrome' } }]
```

**为什么不用 Playwright 自带的 chromium**：本机 npm 走 `127.0.0.1:7897` 代理，`npx playwright install chromium` 反复在 90% 处报 `ERR_SSL_DECRYPTION_FAILED_OR_BAD_RECORD_MAC` / `Download failure`。本机 Chrome 是真实浏览器，对"浏览器真机测试"这个目的完全够用 —— 反正是要验真实排版与滚动，不是验 Playwright 的打包产物。

换一台机器若没装 Chrome，改成 `channel: 'msedge'`，或先跑通 `npx playwright install chromium`。

### 7.2 两个服务由 Playwright 自己拉起

- 服务端：`cwd: '../server'` 跑 `npm run e2e:server`，探活 `http://127.0.0.1:3000/api/health`
- 前端：`npx vite --host 127.0.0.1 --port 5173 --strictPort`

> ⚠️ **前端必须显式 `--host 127.0.0.1`。** `npm run dev` 用的是 vite 默认绑定（`localhost`），而 Playwright 的 `webServer` 探活打的是 `127.0.0.1` —— 实测会一直等到 120 秒超时。这里不改 `client/vite.config.ts` 的 `server.host`：那个文件是给人和局域网平板用的，测试启动方式不同不该反过来改产品配置。

### 7.3 桌面视口

`viewport: { width: 1440, height: 900 }`。依据 `CLAUDE.md` 的「不做的事」：第一版只做桌面浏览器，窗口宽度 ≥ 1280px。

## 9. 改了代码之后，哪些用例必须跟着改

这是本套测试真正起作用的地方 —— 它把散落在 `CLAUDE.md` / `AGENTS.md` 里的「别拆掉」约定变成了会红的断言：

| 你改了什么 | 会红的用例 | 为什么 |
|---|---|---|
| `client/src/features/readalong/ttsCacheKey.ts` **或** `server/src/tts/cacheKey.ts` | `tts-cachekey-parity.test.ts` | 两边必须逐字节一致，否则缓存永远不命中（静默变慢） |
| 句子切分规则（`splitSentences.ts`） | `readalong-split.test.ts` | 锚点的 `charOffset` 与高亮范围会偏（`V1.C` 的 C1 就是为这个做的逐段回归比对） |
| 锚点字段名（`paragraphIndex` 等） | `sync-merge.test.ts` 的「不看 scrollOffset / docVersion」组 | 裁决 2；再造 `paraIndex` 版本会全红 |
| 合并判定（`server/src/sync/merge.ts`） | `sync-merge.test.ts` + `sync-bookmark.test.ts` 的 SY-17~SY-28 | D-11 / D-12 都出在这里，且都不报错 |
| 软删除逻辑 | SY-15「墓碑的 updatedAt 必须刷新」 | 不刷新 updated_at 就永远拉不到墓碑（材料审查 E15） |
| 窗口化几何常量 / `fontSize` 缩放 | `render-virtualwindow.test.ts` | `VD-09` 守着"17 段短文档仍全部渲染"（演示书观感） |
| 图片 `imageId` 算法 **或** `T_ImageResource` 主键 | `cross-document-imageid.test.ts` | 缺陷 D-T01，见报告 |
| 零宽字符表 | `readalong-zerowidth.test.ts` | 缺陷 D-T02，两处口径不一致 |
| 登录页/书架/阅读界面的类名 | `e2e/ui-flows.spec.ts` | 类名是 `CLAUDE.md` 第三节固定的契约，改名要同步改用例 |
| 进度上报的触发方式 | `e2e/sync-two-devices.spec.ts` 的 `scrollReader` | 进度只在 `.reader-scroll` 的 scroll 事件里上报，防抖 1500ms |

## 10. 本套流程**没有**覆盖的

如实列出，避免高估结论。这些和 `docs/02` 第 6.1 节列的一致（其中一部分本轮已经补上）：

| 项 | 状态 |
|---|---|
| 浏览器真机排版 / CSS / 滚动流畅度 | ✅ 本轮已补（Playwright + 真实 Chrome） |
| 多设备同步 | ⚠️ **部分**：用两个独立 browser context 模拟（等价两台设备、走同一真实服务端），**仍未在平板 + 笔记本的真实局域网上跑过** |

| 30 分钟长时间压测 | ❌ 未做 |
| 3000 段以上超大文档 | ❌ 测到 2000 段的几何计算，未测渲染 |

## 11. 常见问题

**Q：`npm test` 报 "No test files found"？**
A：确认在 `server/` 或 `client/` 目录下跑，不是在仓库根。根目录没有 `package.json`。

**Q：端到端一直卡在 `Timed out waiting 120000ms from config.webServer`？**
A：看是不是前端探活超时。`npx vite` 必须带 `--host 127.0.0.1`（见 §7.2）。另外确认 3000 / 5173 端口没被别的东西占着。

**Q：端到端报找不到浏览器？**
A：本机需要装 Chrome（见 §7.1），或改 `channel` / 跑 `npx playwright install chromium`。

**Q：服务端测试偶尔挂住、报 `[vitest-worker]: Timeout calling "onTaskUpdate"`？**
A：这是 **stale vitest worker**，不是代码问题（实测重跑只用 8 秒）。先结束残留的 node 进程再重跑。另外**别用 `Select-Object -Last N` 之类的管道包住 vitest** —— 会挂住它的 worker IPC，重定向到文件更稳。

**Q：`better-sqlite3` 装不上？**
A：这是本仓库最硬的环境坑。`V1.0-merge` 上是 `^12.11.1`（有 Node 24 / ABI 137 预编译包，下载即用）。若在别的分支上遇到 `^13.0.3`，那是已知坑：v13.0.0–13.0.3 的预编译包数量为 0，Windows 上没有 VS Build Tools 必然装不上。

**Q：npm / git 要联网，但代理不通？**
A：环境变量里的 `7900` 端口**没有监听**。实际可用的是 **`7897`**：
```powershell
$env:HTTPS_PROXY='http://127.0.0.1:7897'; $env:HTTP_PROXY='http://127.0.0.1:7897'
# git 用临时参数，不要改全局配置
git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=http://127.0.0.1:7897 fetch
```
