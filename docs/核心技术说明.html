知音漫卷 · 课程设计 · 第一组

核心技术说明

三个子系统的实现原理与所依赖的技术：导入解析、图文混排阅读、逐句高亮跟读。 全部对着代码核实，结论都标了出处文件。

01导入格式与大小限制

支持三种格式，且全部在前端解析（项目裁决 1：服务端只负责存储与分发解析结果， 不引入 EPUB / Markdown 解析依赖）。

格式解析器说明
EPUB epub.js 只取解析结果，不用它的渲染层；按 spine 顺序取正文与插图
TXT 自己实现 parse/txt.ts 按空行分段；第X章/卷/部/篇/回 识别为 h1，第X节 为 h2
Markdown marked 用 lexer 拿标题、段落与图片引用

扩展名判定在 parse/index.ts 的 formatOf，只认 txt / md / markdown / epub。

1.1大小限制

限制项值在哪
单文件上限 500MB parse/index.ts 与 routes/resources.ts 各一份 MAX_FILE_BYTES（同值）；app.ts 的 BODY_LIMIT 也是 500MB
段落数 20000 段 routes/documents.ts 的 MAX_PARAGRAPHS，超了返回 413
单张图片 10MB routes/resources.ts MAX_IMAGE_BYTES
头像 2MB routes/resources.ts MAX_AVATAR_BYTES

前端在读文件之前就用 file.size 预检，超限直接给中文提示（带实际大小）， 不会把 500MB 读进内存再失败。

1.2缓存上限（与导入限制是两回事）

缓存上限淘汰
图片（IndexedDB） 单文档 300 张 或 总量 200MB，先到者为准 按最后访问时间 LRU
音频（IndexedDB） 单文档 60MB 按最后访问时间 LRU

1.3语音合成侧的限制

  • 单句文本 ≤ 500 字（超长句在切分阶段已按 200 字兜底，500 足够宽松）
  • 语速区间 0.5 – 2.0
  • 服务端合成并发 2、队列 8，超限返回 429 RATE_LIMITED
  • 上游超时 20 秒 → 504 UPSTREAM_TIMEOUT；上游失败 → 502 UPSTREAM_TTS_FAILED

02图文混排阅读

图片也是一种「段落」。

段落的类型字段 para_type 有 h1 / h2 / p / img 四种， 图片段在正文流里占一个位置（paraIndex）。 所以图文顺序天然由段落序决定，不需要额外维护"这张图在第几段之间"。

2.1二进制全程不走导入链路

这是这套设计里最关键的一个决策：导入时只传元数据，图片本体在阅读时才懒上传。

  • 解析阶段 —— EPUB 用 epub.js 的 archive（内部是 JSZip）按后缀抽图， 拿到 Blob 存进 imageBlobs: Map<imageId, Blob>； Markdown 用 marked 的词法分析收集引用
  • 导入阶段 —— POST /api/documents 只带 imageRefs: [{imageId, paraIndex, src, alt}]， 一个字节的图片都不传；Blob 写进浏览器 IndexedDB（render/imageCache.ts）
  • 阅读阶段 —— render/LazyImage.tsx 用 IntersectionObserver 判断是否接近视口，参数为 { root: 滚动容器, rootMargin: '200px 0px', threshold: 0.01 }
  • 懒上传 —— 首次进入视口时：先查本地 IndexedDB → 再取服务端 → 服务端也没有（imageUrl 为空）就把本地 Blob PUT 上去。 此后一律经服务端取，前端不直连存储

收益：导入一篇带 300 张插图的 EPUB，上传的只有正文 JSON。

2.2几个踩过的坑

  • 图片段高度固定 200px（.figure-holder 的 min-height）， 所以窗口化渲染的高度估算里，图片段不随字号缩放
  • 图片离开视口要 revokeObjectURL（IndexedDB 副本保留），否则每张图漏一份
  • querySelectorAll('img') 查不到元素自身， 所以 <figure><img/></figure> 这种图片作为直接子元素的结构要单独分支处理，否则漏图
  • epub.js 自身三个坑：必须传 { replacements: 'none' }； archive.getBlob 要求路径带前导斜杠；default 导出有两种打包形态

03逐句高亮跟读

句子是跟读的最小单位，游标由真实的「播放结束」事件驱动——整个链路里没有任何定时器。

R0–R3 用的是 setInterval 假推进，R4 全部删掉换成了这个。 用定时器的话，「高亮位置与音频严格对应」这条验收要求不成立。

3.1切分：纯前端、纯 TS

readalong/splitSentences.ts 实现规则 R1–R10： 句末标点切分、分号冒号不切、引号括号内的句末标点照切、连续省略号只算一次边界、 缩写与小数不切、段内换行归一为空格、超长句 200 字兜底、空句丢弃、索引稳定。

句子在前端切好后随段落一起上传，落 T_Sentence。 只切「参与跟读」的段落（speaksInReadAlong）——标题段和图片段不切， 否则库里会存下阅读器永远用不到的句子。

3.2引擎抽象：这套设计的核心

interface TtsEngine {
  speak(text, opts, signal): Promise<void>   // 念完才 resolve
  preload(texts, opts): void
  stop(): void
}

两个实现的机制完全不同，但对外收敛成同一个接口：

引擎怎么知道「念完了」
ServerTtsEngine 拿到音频二进制，靠 <audio> 的 ended 事件 resolve
BrowserTtsEngine 直接调 Web Speech，靠 SpeechSynthesisUtterance 的 onend resolve

这就是为什么上层的游标推进只写一份。

3.3播放循环

for (let i = start; i < sentences.length; i++) {
  await engine.speak(sentences[i].text, { voice, rate }, ac.signal)
  cursorRef.current = nextIdx
  setCursor(nextIdx)              // ← 高亮在这里推进
  engine.preload(next 3 句)        // 预取后 2 句
}

游标只在 await 返回之后才推进——这就是「高亮位置与音频严格对应」的落地方式。 预取后 2 句（PRELOAD_AHEAD = 2）用来压句间停顿。

3.4两级缓存

// 客户端与服务端各一份实现，必须逐字节一致
sha256([engine, voice, String(rate), text].join('\u0001'))
  • 用 \u0001 做分隔符——直接拼接会有歧义
  • 改一边必须改另一边（ttsCacheKey.ts / server/src/tts/cacheKey.ts）， 否则客户端永远命中不了服务端缓存
  • 客户端 IndexedDB 命中 → 连请求都不发
  • 服务端磁盘 server/data/tts/ 命中 → 回 X-Cache: hit

3.5降级链（自动）

GET /api/tts/engines 里 available=false 的引擎不进前端列表。 Kokoro 没起来时只剩浏览器原生，界面显示「已降级为浏览器发声」， 并明确它 realAudio = false、只支持句子级高亮 （原生接口不返回字级时间戳）。前端不直连第三方服务，一律经服务端代理。

3.6高亮与跟随

  • 句子渲染成 <span class="sent" data-sentence={i}>，i === cursor 时加 sent-active
  • autoScroll 开启时把当前句 scrollIntoView({ block: 'center' })
  • 读者点任意句子 → seek 到那句，同时暂停自动滚动并弹出「继续跟读」提示条 （手动操作优先级高于自动推进）

一句话总结

导入：前端解析、只传结构化结果、图片二进制根本不走导入链路。
混排：图片就是段落，顺序由段落序决定。
跟读：句子是最小单位，游标由真实播放事件驱动，两级缓存按 sha256(engine+voice+rate+text) 对齐。
